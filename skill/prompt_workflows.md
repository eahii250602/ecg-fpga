# 提示词工作流

从本项目（单导联心电 FPGA 前端）开发过程中反复验证过的四类提示词模板。
每个模板给出：**用途 / 提示词原文 / 为什么这样写 / 常见失败模式**。

占位符用 `{{...}}` 表示，使用时替换。

---

## 模板 A：判据先行（最有效的一个）

### 用途
在让模型写任何代码之前，先让它说出「怎么判断这东西是对的」。

### 提示词

```
我要在 {{器件}} 上实现 {{功能}}。
先不要写代码。请先回答三个问题：
1. 这个功能「正确」的判据是什么？给出可测量的量、单位和阈值。
2. 这个判据需要什么激励才能被验证？激励从哪里来？
3. 如果我看到的测量结果与预期不符，最可能错在哪三类地方？
   请按「先查测量、再查前提、最后查设计」的顺序排列。
```

### 为什么这样写
本项目的经验是：**大多数"设计有 bug"其实是"测量方法有问题"**。
统计下来，9 次故障里只有 2 次是真正的 RTL bug，4 次是测试方法错误，
3 次是工具假设错误。先让模型把判据和激励说清楚，能提前暴露「测法错误」。

### 常见失败模式
- 模型直接给代码 → 追问「先回答问题 1」。
- 判据含糊（"结果正确"）→ 要求给出单位和阈值（如"误差 ≤ 2 LSB"）。

## 模板 B：定点化的可行性与代价

### 用途
判断一个滤波/算法在给定位宽下能不能实现，代价多大。

### 提示词

```
算法：{{算法}}，系数 {{列出系数}}。
目标字长：{{N}} 位定点，格式 {{Qi.f}}。
请：
1. 检查每个系数是否超出该格式的可表示范围，列出超出的。
2. 估算量化误差经过反馈环后被放大多少倍（给出推导）。
3. 给出 2~3 种替代实现的误差估算，并说明各自的代价（精度/资源/延迟）。
4. 最后给一句结论：在 {{N}} 位下是否可实现；若不可实现，应把哪个环节移到别的域。
```

### 为什么这样写
本项目里 0.5 Hz 数字高通的 `b1 = -1.9823` 超出 Q1.15（±1）范围，
会被**静默截断**为 −1.0，滤波器失效且不报错。
让模型主动检查「系数是否超出格式范围」能避免这类静默失效。

### 常见失败模式
- 模型只说"精度够用" → 要求给出具体误差数值（LSB）。
- 忽略反馈环放大 → 明确要求"给出推导"。

## 模板 C：时序不收敛的定位

### 用途
Vivado 报负 WNS 时，先判断是「结构问题」还是「约束问题」。

### 提示词

```
Vivado 报告 WNS = {{值}} ns，失败端点 {{N}} 个，约束周期 {{T}} ns。
失败路径的起点/终点分别是 {{起点}} / {{终点}}。
请：
1. 判断这是组合逻辑太深、还是跨时钟域、还是约束本身不真实。
2. 若为组合逻辑太深：给出「插寄存器」的具体位置建议，
   并估计每插一级能改善多少。
3. 若为跨时钟域：指出应该用什么同步结构。
4. 给出一个「改完之后如何验证确实变好了」的判据。
```

### 为什么这样写
本项目的 HRV 模块曾 WNS −4.102 ns，根因是同一个表达式
`(drr[15]?-drr:drr) * (drr[15]?-drr:drr)` 被综合成**两个乘法器**。
让模型先区分「结构 / 跨域 / 约束」三类，能避免盲目改约束。

### 常见失败模式
- 模型建议"降低时钟频率" → 这不是优化，是回避；要求给出结构性方案。
- 没有给验证判据 → 追问。

## 模板 D：上板数据与仿真不一致

### 用途
仿真通过但板上结果不对时的系统化排查。

### 提示词

```
仿真结果：{{仿真值}}
板上实测：{{实测值}}
差异：{{描述差异}}（例如"恰好 2 倍"、"恒为 0"、"偶尔错一个"）。
我的设计里有这些可观测点：{{列出可用于回读的寄存器/信号}}。
请按以下顺序帮我排查，每步给出具体要读的值和判据：
1. 前提假设（时钟频率、复位极性、寄存器地址）
2. 激励是否真的加上了
3. 数据通路（逐级回读）
4. 测量方法本身
```

### 为什么这样写
本项目的三次典型故障都靠这个顺序定位：
- 「恰好 2 倍」→ 时钟是 62.5 MHz 而非文档写的 100 MHz
- 「恒为 0」→ 0x00 是双用途寄存器，先写频率字时被当成样本写掉
- 「偶尔错一个」→ DMA 地址步长 2 倍导致跨样本

### 常见失败模式
- 模型跳到第 3 步直接猜设计 bug → 强制它先回答第 1、2 步。
- 「可观测点」为空 → 先补观测通路，再排查（见模板 E）。

## 模板 E：补可观测性（元模板）

### 用途
当系统"什么也看不见"时，先让它可观测，再谈调试。

### 提示词

```
我的系统现在表现出 {{现象}}，但没有任何内部信号可以回读。
请设计一套最小的观测通路：
1. 最少需要暴露哪几个内部信号？为什么是这几个（信息量最大）。
2. 用什么机制暴露（虚拟寄存器 / ILA / 打印）？各自的资源与时间代价。
3. 暴露之后，什么样的读数组合能唯一确定故障位置？给出判定表。
4. 这套观测通路在问题解决后，应该保留还是删除？为什么。
```

### 为什么这样写
本项目在 Pan-Tompkins 检测数停滞时，花了三小时猜测「链路失效 / 漏检 / 阈值失配」
三种互斥解释；最后用十余行 RTL 加两级观测（内部积分和回读 + 检测事件打标），
十分钟内定位。**观测成本远低于试错成本。**

## 通用规则（写提示词时始终遵守）

1. **一次只问一件事**。要求模型同时做三件事，它会把三件都做浅。
2. **要求给出数值，不接受形容词**。"精度够用" → "误差 ≤ 2 LSB"。
3. **要求给出判据**。任何结论都要能被证伪。
4. **让它先复述你的约束**。模型经常漏掉你给的约束（位宽、时钟、地址）。
5. **失败时不要重复同一个提示词**。先问「你刚才的假设是什么，哪个可能错了」。
