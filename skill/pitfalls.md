# 踩坑清单（Pitfalls）

> 本项目开发过程中真实踩过的坑。**每条都注明"是否静默失效"**——静默失效类最危险，因为它不报错。
>
> 用途：① 自己复盘 ② 竞赛"大模型协作与技能包"评分材料 ③ 队友上手时的避坑指南。

---

## ⚠️ A 类：静默失效（不报错，但功能全错）—— 最危险

### A1. `$readmemh` 用相对路径 → ROM 读不到数据

| 项 | 内容 |
|---|---|
| **现象** | 仿真里 `ecg_wave` 显示为 `XXX`；综合后波形是一条直线 |
| **原因** | `$readmemh("ecg_256x12.mem", mem)` 用的是**相对路径**，而仿真/综合的工作目录不是文件所在目录 |
| **为什么危险** | **不报错**。Vivado 只在 `$readmem` **失败**时静默处理，波形全 0，肉眼只看到"没有心跳" |
| **解决** | 用**绝对路径**：`parameter MEM_FILE = "D:/ecg/vivado_src/ecg_256x12.mem"` |
| **验证方法** | 综合日志里搜 `[Synth 8-3876]`，必须看到 **`$readmem data file '...' is read successfully`** |
| **长期改进** | 改用 Block Memory Generator IP + `.coe`，把数据固化进 IP，彻底摆脱路径依赖 |

### A2. `MEM_FILE` 参数"透传覆盖"

| 项 | 内容 |
|---|---|
| **现象** | 同上：ROM 读不到数据，波形变直线 |
| **原因** | `dds_ecg` 有 `MEM_FILE` 参数，且**透传给内部 `ecg_rom`**（`.MEM_FILE(MEM_FILE)`）。只改 `ecg_rom` 的默认值为绝对路径，会被 `dds_ecg` 的**相对路径默认值覆盖** |
| **为什么危险** | **不报错**。属于"改了但没生效" |
| **解决** | **参数链上每一层都要改**：`dds_ecg` 和 `ecg_rom` 的 `MEM_FILE` 默认值都改成绝对路径 |
| **教训** | 遇到"参数化设计"，**要沿参数传递链逐层检查**，不能只看最底层 |

### A3. PS 的 `FCLK_CLK0` 默认是 **50 MHz**（不是 100）

| 项 | 内容 |
|---|---|
| **现象** | 上板后心率读数**只有真实值的一半**；不响应期实际变成 400ms，会漏检心跳 |
| **原因** | IP 里的参数按 **100MHz** 编写（`CLK_FREQ_HZ = 100_000_000`，`TICK_DIV = 400000` → 250Hz 采样）。但 Zynq PS 给 PL 的 `FCLK_CLK0` **默认输出 50MHz** |
| **为什么危险** | **不报错**。真实采样率 = 50e6 / 400000 = 125Hz，只有设计值的一半，整条标定链全错 |
| **解决** | 双击 PS 方块 → `Clock Configuration` → **`FCLK_CLK0` 改为 100.000** |
| **注意** | `Input Frequency = 33.333333 MHz`（板载晶振）**默认就是对的**，不要动 |
| **教训** | **PL 逻辑的时钟来自 PS，不是板上晶振**。设计前必须先确认 PS 给的频率 |

### A4. `component.xml` 手工编辑会被 Vivado 覆盖

| 项 | 内容 |
|---|---|
| **现象** | 手工在 `component.xml` 里补的文件登记项，关闭工程后**全部消失** |
| **原因** | IP 元数据由 **Vivado 的 IP 打包器**管理；工程保存/关闭时会用内存中的模型回写 |
| **解决** | 必须通过 GUI 的 `Package IP` 视图（或 `Re-Package IP`）维护；或者在 **Vivado 已关闭**时改 |
| **附带发现** | Vivado 2026.1 的 `.bd` 文件是 **JSON 格式**（不是 XML），配置就存在里面，**保存后可读可核对** |

## 🔧 B 类：会报错 / 现象明显类

### B1. FTW 量级写错（差 10⁶ 倍）

| 项 | 内容 |
|---|---|
| **现象** | 波形变成密集噪声，完全不是心跳 |
| **原因** | `FTW = 2³² × f_out / f_clk`。125MHz 下 60BPM 应为 **34**，却写成了 **34,359,738** |
| **解决** | 用**位宽足够的整型运算自动推导**：`(TWO32 * f + CLK/2) / CLK`，不手算 |
| **教训** | 频率控制字这种"小整数"最容易漏算量级，**能用公式算就别手填** |

### B2. 32 位延时常量溢出

| 项 | 内容 |
|---|---|
| **现象** | 仿真在 1,000,001 µs 就结束了，而不是预期的 3,500,001 µs |
| **原因** | Verilog 里 `#2_500_000_000` 是**有符号 32 位**，上限仅 **2,147,483,647**。超限后变负数，被当作 0 |
| **解决** | 拆成 `#1_500_000_000; #1_000_000_000;` |
| **教训** | Verilog 的时间字面量默认是 32 位有符号，**超过 21.4 亿就要拆** |

### B3. Testbench 时钟沿竞争

| 项 | 内容 |
|---|---|
| **现象** | 波形窗口里 `r_detect` 脉冲**完全看不见**（宽度为 0） |
| **原因** | 在 `@(posedge clk)` 的同一时刻改变 `sig_valid` → 组合逻辑输出被瞬间改变，脉冲宽度为零 |
| **解决** | 在时钟沿后加延时：`@(posedge clk); #1 sig_valid = 1'b1;` |

### B4. Vivado 未打开工程时找不到 "Create and Package New IP"

| 项 | 内容 |
|---|---|
| **现象** | `Tools` 菜单里没有这个选项 |
| **原因** | 当时停在 Vivado 的**欢迎/启动页面**，没有打开任何工程 |
| **解决** | 先打开任意工程，菜单项才出现 |

### B5. Windows 文件锁：Vivado 开着工程时删不掉工程目录

| 项 | 内容 |
|---|---|
| **现象** | 删除工程目录报"文件正由另一进程使用"（`.pb` 文件） |
| **原因** | Vivado 用内存映射方式打开 `.pb`（内部数据库缓存），进程不退出就锁着句柄 |
| **解决** | 先在 Vivado 里 `File → Close Project`（或关闭 Vivado），再删 |

## 🏗️ C 类：工程结构与可复现性

### C1. 母版与工程内副本"分叉"

| 项 | 内容 |
|---|---|
| **现象** | `D:\ecg\vivado_src\ecg_rom.v`（相对路径，不能跑）与工程内 `imports\vivado_src\ecg_rom.v`（绝对路径，能跑）**内容不一致** |
| **为什么危险** | 仿真能跑是因为用了**副本**；一旦改母版或拷贝母版，就会踩 A1 |
| **解决** | 明确**单一事实来源**（母版），改完立刻同步；或干脆只用一处 |

### C2. IP 不自包含（影响"可复现性"评分）

| 项 | 内容 |
|---|---|
| **现象** | IP 的 `component.xml` 里，7 个源文件中有 **5 个指向 IP 目录外部**（`../edit_ecg_axi_v1_0.srcs/sources_1/imports/vivado_src/*.v`）；`.mem` 用**绝对路径** |
| **后果** | ① 删掉 `edit_ecg_axi_v1_0.srcs\` → 正式工程直接崩<br>② 换机器 → `.mem` 绝对路径失效 |
| **解决** | 把 5 个 HDL 放进 IP 自己的 `hdl\`，改 `component.xml` 路径为相对路径；`.mem` 改用相对路径或 BMG IP |
| **⚠️ 注意** | **修改必须在副本上做**，不要动正在使用的 IP |

## 🧩 D 类：流程与协作坑（工具链之外的坑）

### D1.「假核对」：把磁盘上不存在的代码写成"已核对通过" —— **本项目最严重的一次**

| 项 | 内容 |
|---|---|
| **现象** | 助手核对时，`grep` 输出显示某信号**只出现在端口声明行**（说明它没有任何赋值）。但助手在结论里写下了"✅ 该赋值语句已存在（本次新加）"——**这条证据在输出里根本不存在** |
| **直接后果** | `reg_wave_addr` 无驱动源 → Vivado 报 `Synth 8-3848 ... does not have driver`，该信号被固定 → **Python 读波形时会永远读到同一个点**（又一个静默失效） |
| **如何被发现** | **只有综合日志抓住了它**。人工代码审阅和"看起来对"的判断都没抓住 |
| **根因** | ① 助手**最初漏交代**这条改动（指令漏项）；② 用户执行后，助手的核对环节**用"我下过指令"推断"应该存在"，而不是看证据** |
| **纠正措施** | 建立**核对规则 R1~R5 与指令规则 I1~I4**（见 `report/working_agreement.md` §2.5） |
| **最大的教训** | ★ **"已核对"必须有原文行号背书；没有行号的 ✅ 是假的 ✅**<br>★ **工具不会撒谎，人工核对会**——所以每一步都要让**综合器 / DRC / 日志**来当第二裁判<br>★ **指令过长是风险**：一条消息塞 3 项以上改动，漏项概率显著上升 |

### D2. 人工核对与工具验证的优先级

| 手段 | 可靠性 | 结论 |
|---|---|---|
| 凭记忆/推断 | ❌ 最不可靠 | 禁止用于下结论 |
| 人工读代码 | ⚠️ 中等 | 只能用于**提出怀疑**，不能用于**确认通过** |
| **grep 并引用行号** | ✅ 较高 | 核对的基本要求 |
| **综合/实现日志、DRC、时序报告** | ✅✅ 最高 | **最终裁判**——它们由工具算出，不会因人的期望而改变 |

> **本项目已两次由"工具"救回**：一次是 `$readmem` 静默失效（靠综合日志的 `read successfully` 确认），一次是本次无驱动（靠 `Synth 8-3848` 发现）。

### D3. 文件权限：**工作区外的写操作必须显式提权**，否则被沙箱拒绝（2026-10-23 记录）

| 项 | 内容 |
|---|---|
| **现象** | 助手写/改 `D:\ecg\...` 的文件、或跑带 `D:` `E:` 路径的 shell 命令时，返回：`[sandbox: file access denied under workspace-write mode]` |
| **原因** | 会话有"文件策略"（本次为 **workspace-write**）：**只允许改会话工作区内的文件**。本会话工作区是<br>`C:\Users\yeahrizzi26\Documents\deepseek-harness\default-workspace`，而项目在 **`D:\ecg`** —— 在工作区之外 |
| **为什么费时间** | 不报错、不崩溃，只是**静默失败一次**；助手如果不懂，会以为"不能写"，于是放弃写文件、只在聊天里给文本（这正是用户早期遇到的困扰） |
| **解决** | 拒绝信息里其实已经给了办法：<br>`escalation available — retry this exact operation once with sandbox_permissions + justification`<br>→ **原样重试同一个操作**，并带上<br>`sandbox_permissions: "danger-full-access"` + 一句 `justification`（用用户的语言写为什么需要）<br>→ 用户会看到一个**批准提示**，同意后即执行成功 |
| **⚠️ 关键细节** | **批准不是"记住一次就永久生效"**：之后每一次对工作区外路径的写操作，**调用里都必须重新带上这两个参数**。本次会话中唯一一次漏带（改 `HANDOFF.md`）就又被拒了一次 |
| **哪些操作需要** | 需要：`write` / `edit` / 一切 shell 命令（只要路径在工作区外）<br>**不需要**：`read` / `grep` / `glob` 读文件——本次会话读 `D:\ecg`、`E:\vivado` 全程未被拒 |
| **两种模式** | 当前已是 `workspace-write`，所以"更宽的下一级"就是 `danger-full-access`（中间没有别的档位） |
| **★ 根治办法（最省事）** | **把新会话的工作目录设成 `D:\ecg`** —— 项目文件就都在工作区内了，从此**永远不弹批准、不需要提权参数**。若做不到，就在每次调用里带参数 |
| **诚实说明** | 官方设计是"先被拒 → 再原样重试提权"。**主动第一枪就带参数**严格说是省时间用法（每次仍会弹一次批准，除非已用上面的根治办法）。两条路都可行 |
| **给新窗口的交代** | 在开场指令里明写这条规则（见 `HANDOFF_ECG.md`），助手就不会浪费一轮往返 |

**⚠️ 但必须分清两类"被拒"，别误诊（2026-10-23 补）**：

| 类型 | 特征 | 正确处理 |
|---|---|---|
| **① 预期内的隔离拒绝**<br>（本项目遇到的就是这类） | 提示里写明了 `under workspace-write mode`，且带 `escalation available`；**目标是工作区之外**的路径 | **按上表带参数提权重试**。<br>**不需要修 ACL**——这是策略正常生效 |
| **② 意料之外的拒绝** | 连**工作区内部**的文件也写不了 / 目录列不出来；或一个**本来能读**的路径突然读不了 | 这不是策略问题，是 Windows **ACL（访问控制列表）**坏了 → 调用内置技能 **`diagnose-windows-sandbox-acl`**：它会在同一次运行里检查该路径**及其每一级上级目录**，并修好它能证明的 ACL 问题 |

> **判据很简单：看目标是"工作区内"还是"工作区外"。** 工作区外 → 提权（①）；工作区内还失败 → 修 ACL（②）。

### D5. `0xC0000142`：命令执行通道整条挂掉 → **升权重试**（2026-10-26 本窗口实录，修正 2026-10-23 旧结论）

> ⚠️ **与 D3 不是一回事**：D3 是"策略拒绝某个路径"（提示里写明 `workspace-write`、带 `escalation available`）；
> D5 是"**进程根本创建不出来**"（任何命令都失败、且**无任何输出**）。

| 项 | 内容 |
|---|---|
| **现象** | 任何 shell 调用都只返回 `0xC0000142`，且**完全没有输出**。连 `pwsh` 跑 `Write-Output hi`、连 `cmd /c where` 都失败。调 Python / Node 更是全挂 |
| **最大的误诊陷阱** | 很容易以为是"Python 坏了 / 路径不对 / 虚拟环境错 / 环境变量错"，于是花大量时间去查解释器和 PATH——**全部白费**。<br>**判据：连不依赖任何程序的 `Write-Output` 都挂 → 是"进程创建"失败，不是你的命令有问题** |
| **错误码含义** | `0xC0000142` = `STATUS_DLL_INIT_FAILED`（进程创建时 DLL 初始化失败）。常见诱因：桌面堆/句柄耗尽、安全软件注入 DLL、控制台与管道继承异常、会话状态异常 |
| **★ 解法（真正起作用的"二次请求"）** | **对同一条命令加 `sandbox_permissions: "danger-full-access"` + 一句 justification 重试（等批准）**。2026-10-26 本窗口实录：前台/后台裸跑都 0xC0000142，升权后同一条命令**立即成功**；"二次请求"= 第二次调用带了升权并被批准 |
| **为什么升权能成（勘误：不是后台）** | 根因是 **workspace-write 沙箱的受限令牌**让子进程在 DLL 初始化阶段失败（0xC0000142）；升权 = 该条命令不再跑在受限令牌下，所以能起来。<br>**后台任务默认仍跑在同一沙箱里 → 实测照样 0xC0000142**（job pwsh-16 / pwsh-26 均退出 3221225794）——别再把"改后台"当解法 |
| **附带发现** | ① 原样重试一次有时会自愈（偶发桌面堆瞬时耗尽）<br>② **批准不延续**：后续每条 shell 命令、每个 D:\ecg 文件写操作都要重新带 `sandbox_permissions: "danger-full-access"` + justification<br>③ **文件工具（read / write / edit / grep / glob）不经过进程创建，命令通道全挂时仍可用**——结论要往文件里写 |
| **正确顺序** | 见下方"三步走"：不要一上来就查环境 |

**命令通道故障·三步走（新窗口照抄）**：

```
第 0 步  探针：跑一条最贱的命令        pwsh("Write-Output hi")
         有输出 → 通道正常，问题在别处，停止用本方案
         0xC0000142 或空输出 → 进入第 1 步

第 1 步  原样重试一次（排除偶发）      同一条命令，再发一次

第 2 步  ★ 对同一条命令升权重试（关键一步）
         pwsh("同一条命令", sandbox_permissions: "danger-full-access", justification: "…")
         ✅ 成功 → 后面所有较重命令、所有 D:\ecg 写操作一律照此带参数（批准不延续）

第 3 步  仍失败 → job_list 看作业是否堆积 → 刷新 GUI 页面 / 重开窗口
         （可选，未验证：后台任务也带 danger-full-access 作为长任务通道）
```

> **一句话记住**：`0xC0000142` 且**无输出** = 进程起不来；**别查配置，对同一条命令挂 danger-full-access 重试（后台不顶用）**。

### D6. PYNQ 上直接读 /dev/mem 前忘了加载比特流 → 全部寄存器读回 0（2026-10-26 板上实录）

| 项 | 内容 |
|---|---|
| **现象** | Python 脚本用 mmap 读 PL 寄存器（如 XADC `0x43C10000`），**所有值都是 0**，脚本还"正常跑完"，看起来像"外设没工作 / 数据通路坏了" |
| **根因** | PYNQ 开机后 **PL 是空的**（不会自动加载比特流）；未配置的 PL 对 /dev/mem 读取返回 0。自测脚本若只读 /dev/mem、不先 Overlay，必然全 0 |
| **判据** | ① 读 `ecg_axi` 的 VERSION（`0x43C00014`）应为 `0xEC600001`——不是就说明 PL 没在跑本设计；② 正确流程：先 `ol = Overlay('ecg_bd.bit')`，从 `ol.ip_dict` 取 `phys_addr`，再 MMIO 读 |
| **正确写法** | `from pynq import Overlay; ol = Overlay('/home/xilinx/ecg_bd.bit')` → `ol.ip_dict['xadc_wiz_0']['phys_addr']` → `MMIO(base, 0x400).read(0x200+4n)` |
| **教训** | **"读回 0" ≠ "外设坏"**，先查"PL 有没有加载"。任何板级自测脚本都必须自带 Overlay 加载 + VERSION 自检 |

### D7. 忘了 source XRT 环境 → `RuntimeError: No Devices Found`（2026-11-03 板上实录）

| 项 | 内容 |
|---|---|
| **现象** | `python3 pt_check.py` 直接崩：`UserWarning: No devices found, is the XRT environment sourced?` → `RuntimeError: No Devices Found`（`pynq/pl_server/device.py`） |
| **根因** | `sudo -s` 得到的是一个**全新的 root shell**，之前 shell 里 source 过的 `xrt_setup.sh` 不会继承；`pynq` 库靠 XRT 枚举 FPGA 设备，没有 XRT 环境就找不到设备 |
| **判据** | 报错里出现 `is the XRT environment sourced?` 就是这个坑；补 `source /etc/profile.d/xrt_setup.sh` 后立刻正常 |
| **正确流程** | 每次新开（或 `sudo -s`）的 shell：`source /etc/profile.d/pynq_venv.sh` **和** `source /etc/profile.d/xrt_setup.sh` 两句都要 |
| **教训** | 环境变量**不跨 shell 继承**；板级脚本前先确认两行 source，再怀疑代码 |
