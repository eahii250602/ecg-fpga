**四条根因（比结论更值钱）**：
1. **把文档当事实**：`FCLK=100MHz` 只是 BD 里的设置值，PS 时钟实际由 BOOT.BIN 的 ps7_init 决定，那个 100 从未在运行时生效——**项目第一天就埋下的错误假设**；
2. **没有"异常先测时基"的纪律**：任何"计数/时间/速率"异常，第一步该验采样率与时钟，我们却先改算法；
3. **原始数据被期望值压住**：6 秒仅 ~900 点、只有 4 个检测事件，**两次原始事实都指向"实际速率低于预期"**，却被"应该 7 拍"盖过去；
4. **仿真越绿越说明问题在仿真外**：理想的 10ns 时钟下怎么改都全过 → 该怀疑时基而非逻辑。

**沉淀的方法**：① 单一寄存器读数不下结论（多源交叉验证）；② 先证明"算法对"再找"环境错"；③ 可观测性优先（调试通道成本远低于盲改）；④ 一个错误前提会派生多个假问题（180BPM 卡死、6 秒 4 拍、rr 不更新，全是同一个根）。

### 2026-11-04 00:40 —— 采样时基：sleep → perf_counter 忙等（误差 3.3% → 0.00%）

| 条目 | 内容 |
|---|---|
| **问题** | `time.sleep(0.004)` 粒度约 1ms，实测平均 **4.13ms**（误差 **3.3%**）→ 实际采样率 242Hz。滤波器系数按 250Hz 设计，50Hz 干扰会被"看成" **51.65Hz**，而陷波 -3dB 带宽只有 **48.11~51.91Hz（±1.9Hz）** → **偏离 1.65Hz，抑制比从 -53dB 掉到 -3dB**。这是 2026-11-03 那个 -3.4dB 结论之外的另一个隐患 |
| **做法** | 用 `time.perf_counter()`（纳秒单调时钟）**忙等到绝对时刻**：`deadline = t0 + (i+1)/fs; while pc() < deadline: pass;` **先等后读**——若先读后等，读操作耗时会累积成时间偏移 |
| **本地实测（PC，模拟 1µs 读取开销）** | 400 点 @250Hz：**mean = 4.000 ms，误差 −0.00%，抖动 std = 11.1 µs**，最大偏差 121.4 µs（Windows 调度一次抢占）。对比 sleep 方案的 4.13ms / 3.3% / ±130µs |
| **换算** | 采样率 250.00Hz → 50Hz 干扰落在 **50.00Hz**，偏离陷波中心 **0.00Hz**（原来 1.65Hz）→ **硬件陷波器第一次真正对准真实 50Hz** |
| **代价** | 忙等占满一个 CPU 核；250Hz 采集只占约 0.5% 实际工作，其余是空转。短时采集（秒级）完全可接受；长时间采集应改用硬件定时（D9/D10 的 DMA） |
| **产物** | `board/sd_upload/ecg_timebase.py`（可复用精确采样/推送模块）、`rate_check.py`（新旧方案对比 + 换算成陷波偏移）、`host_ecg.py` 改用新时基 |
| **方法学** | ① 把"误差"换算成"对系统指标的影响"（采样率误差 → 陷波偏移 → 抑制比），才能判断值不值得改；② 先在 PC 上用假设备验证时序代码，再上板——避免把"代码错"和"板子慢"混在一起 |
| **注意** | 这是**软件层**的提升，与 v5 的 RTL 改动无关。v5 只负责"把真实样本接进硬件链"，时基精度靠本项 |
