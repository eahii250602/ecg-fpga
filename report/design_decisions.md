| D-02 | 32 位相位累加 + 8 位相位截断 | 保 0.023Hz 分辨率的同时，ROM 从 4G 点降到 **256 点（3Kbit）** |

| D-07 | 200ms 生理不响应期 | T 波峰值 614 也超阈值，**不屏蔽会让心率翻倍** |
| D-08 | **除法放 Python，硬件零 DSP** | 心率几秒更新一次，实时性要求低；**硬件除法要占 DSP 且压时序** |
| D-09 | RR 计数 16 位 | 250Hz 下 20BPM 对应 750 点，16 位（65535）留 **87 倍余量** |
| D-10 | **AXI4-Lite** vs AXI4-Full | 只需读写几十字节寄存器；**Full 的突发能力用不上** |
| D-11 | 全链路单一时钟域 | 避免跨时钟域（CDC）同步器与亚稳态风险 |
| D-12 | 一个 IP 封装全部逻辑 | Block Design 只需"拖一个方块连一根线"，**接口最干净** |
| D-13 | 寄存器穿透传信号 | 改动最小；不需引入额外总线协议 |
| D-14 | 小 ROM 用查找表 vs BRAM | 3Kbit 用最小 18Kbit 的 BRAM **浪费 6 倍**；查找表更省 |

| D-16 | 不装板卡文件，用通用器件 | 本设计 PL 侧**无外部引脚**，不需要引脚约束；PS 由 PYNQ 启动镜像配置 |
| D-17 | 工作区不重排，另建提交包 | IP 引用外部路径 + `.mem` 绝对路径，**重排直接搞崩工程** |
| D-18 | **IP 自包含化 + 数据内嵌** | 换取"换机器可用"+"物理上不可能静默失效"，代价仅 60 行代码 |
| D-19 | 环形缓冲 1024 点 × 32 位 | 4 秒 ≈ 5 个心跳；32 位对齐**省去 Python 拆包** |
| D-20 | **寄存器间接读 vs AXI BRAM Controller** | 采集 1024 点需 4096ms，读取仅约 2~4ms（含 Python 开销），**只占波形跨度的 0.1%**（详见勘误 E-01） |
| D-21 | 复用从机空寄存器槽 | 原 6 个寄存器中 2 个是空槽，**正好够用，零新增** |
| D-22 | 仿真用 1.25MHz 缩放时钟 | 全速仿真一次心跳要上亿时钟；缩放后**逻辑等价、快 80 倍** |
| D-23 | 设计全面参数化 | 仿真可覆盖时钟参数，**资源与行为完全不变** |

## ⚠️ 勘误与补充（V4 阶段，2026-10-07）

### 勘误 E-01 · 更正 D-20 的量化数字

**原记录（不准确）**：
> "读 1024 点只需 **0.3 毫秒**，比采样速度快 **3000 倍**"

**错在哪**：
1. **只算了硬件，漏了软件**：0.3ms 只是 AXI 协议耗时；PYNQ 的 `mmio.read/write` 每次还有 **0.5~2µs** 的 Python 调用开销，2048 次调用约 **1~4ms**——**这才是主要耗时**。
2. **两个数字互相不自洽**：4096ms ÷ 0.3ms ≈ 13600，不是 3000。

**更正后的准确数据**：

| 环节 | 耗时 |
|---|---|
| AXI 硬件协议（2048 次寄存器访问 × 约 100ns） | 约 **0.15 ~ 0.2 ms** |
| Python 调用开销（2048 次 mmio 调用） | 约 **1 ~ 4 ms** |
| **合计** | **约 2 ~ 4 ms** |

**更正后的论证方式（更严谨、经得起追问）**：

```
   波形时间跨度：1024 点 ÷ 250Hz = 4096 ms
   读取耗时    ：约 2 ~ 4 ms
        ↓
   读取耗时仅占波形时间跨度的 【0.05% ~ 0.1%】
   = 读取几乎"瞬间完成"，远快于需求
```

**更正后的答辩词**：
> "我们评估过 AXI BRAM Controller 方案。本项目的波形是 250Hz 的慢信号——采集 1024 点需要 4.1 秒，而用寄存器间接读取，**AXI 硬件本身只花约 0.2 毫秒，即使算上 Python 调用开销也在几毫秒量级，只占波形时间跨度的千分之一**。因此选择了不增加 IP、不改动 Block Design 的简化方案——这是有依据的取舍，不是能力不足。"

**从这次更正得到的教训**（重要）：
- 做方案对比时，**必须把"硬件 + 软件"两部分耗时都算进去**，只算硬件会低估一个数量级
- **给出的倍数必须能由给出的绝对值用同一公式推出**——不然一问就露馅

### 勘误 E-02 · V3 与 V4 的综合流程不同，资源数字**不可直接比较**

**事实（有文件证据）**：

| | V3（19:05 报告） | V4（23:09 报告） |
|---|---|---|
| `.runs` 下的运行目录 | **4 个 OOC 目录**（`ecg_bd_ecg_axi_0_1_synth_1` 等） | **只有顶层 `synth_1`** |
| 综合流程 | **OOC（IP 独立综合，边界冻结）** | **内联 / 全局（整设计拍平综合）** |
| Slice LUTs | **556** | **535** |
| Slice Registers | **715** | **665** |
| Block RAM | 0 | **1** |
| WNS | +3.831 ns | +3.428 ns |

**为什么"加了 BRAM 反而更省"**：

```
   内联综合让优化器能【跨模块边界】动手
        → 原先在 OOC 边界处无法删除的冗余逻辑被合并掉
        → 抹掉的（约 90 个触发器 + 若干 LUT）多于 V4 新增的（约 42 个触发器 + 1 块 BRAM）
        → 净结果：更省
```

**流程为什么会变（⚠️ 推测，未证实）**：

```
   发生在"删除 ecg_system.gen → 重开工程 → 重新 Generate Output Products"那一步
        ↓
   推测：重建产物时未恢复原有的 OOC 运行设置，改用全局（内联）综合
        ↓
   依据：时间上紧邻（删 .gen 之前有 OOC，之后没有）；但我没有 V3 时刻的设置快照可对比
```

**影响评估**：

| 方面 | 影响 |
|---|---|
| 资源占用 | ✅ 更省（−21 LUT / −50 FF） |
| 时序 | ✅ 仍通过（WNS +3.428ns，余量 34%） |
| 迭代速度 | ⚠️ 改任何 IP 源码都需全设计重综合（本设计仅约 1 分钟，可接受） |
| **数字可比性** | ❌ **与 V3 的数字不能直接比大小** |

**教训（重要）**：

> ★ **比较两次资源数字之前，必须先确认"两次的综合流程是否相同"。**
> ★ **不同流程的数字不能直接比大小**——否则会把"流程差异"误读成"设计变化"。
> ★ 另附：本次对比中还曾**误把练习工程（SmartConnect 版）的 554/692 当成 `ecg_system`（AXI Interconnect 版）的数字**（后者实为 556/715）。
>    **教训：报数字必须写明"来自哪个工程的哪份报告"。**

### 新增决策 · V4 落地时的三个取舍

#### D-24 · 用 BRAM 实时缓冲波形，而非"让 Python 直接读 ROM 模板"

| 项 | 内容 |
|---|---|
| **备选方案** | ① **直接读 ROM 模板**：把 256 点 ROM 内容经 AXI 暴露，Python 按 FTW 推算时间轴"重建"波形 ② **BRAM 实时缓冲**：把 DDS 实际输出的采样值存入环形缓冲供 Python 读回 |
| **选择** | **② BRAM 实时缓冲** |
| **量化依据** | ① 方案①理论可行（DDS 确定性，波形 = 模板循环）且**不占 BRAM**；但它读到的是**模板**，不是"实际采样序列"。② 方案②读到的是**真实采样值**，能反映阈值判断与检测时刻，对未来扩展（滤波、异常标记）天然兼容。③ 资源代价：1024×32bit = **32 Kbit = 约 2 块 BRAM18**，而当前 BRAM 占用为 **0 / 140** |
| **付出的代价** | 占用约 2 块 BRAM + 约 40 行 RTL |
| **为什么可接受** | BRAM 空闲 100%（0/140）；且**"实时采样"正是本项目"监测系统"定位的核心证据**——若只显示模板，会被质疑"这不就是查表吗" |

#### D-25 · 单缓冲即可，不需要双缓冲（乒乓）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 双缓冲：一块在写、一块在读，读时切换 ② **单缓冲环形** |
| **选择** | **② 单缓冲** |
| **量化依据** | 读取整帧（1024 点）耗时约 **2~4 ms**，而采样周期为 **4 ms**（250Hz）——即**读完一整帧的时间里，写指针最多前进约 1 个点**，读取期间缓冲区内容**基本是冻结的**，画面不会撕裂 |
| **付出的代价** | 理论上画面可能有 ≤1 个采样点的错位（视觉不可察觉） |
| **为什么可接受** | 用"1 个采样点的理论错位"省掉整套双缓冲切换逻辑（地址选择、状态机、额外一块 BRAM）——典型的"用可忽略代价换显著简化" |

#### D-26 · 波形在 BRAM 中占满 32 位（而非紧凑存 12 位）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 紧凑存 12 位（两个点挤进 3 字节） ② **符号扩展存 32 位** |
| **选择** | **② 32 位** |
| **量化依据** | 浪费 1024×20bit = **20 Kbit**（约 1 块 BRAM18）；而 BRAM 空闲 **2520 Kbit**。收益：Python 读到的就是**标准 32 位有符号整数**，无需任何位操作拆包 |
| **付出的代价** | 多占约 1 块 BRAM18（占用率 0% → 约 1.4%） |
| **为什么可接受** | 仍有 **98.6% 的 BRAM 空闲**；换来 Python 侧代码量大幅减少、出错概率降低 |

# 一、系统架构级决策

## D-01 · 用 DDS 合成心电波形，不用真实心电采集

| 项 | 内容 |
|---|---|
| **备选方案** | ① AD8232 模拟前端 + 电极，采集真实心电 ② DDS 在 FPGA 内合成标准心电波形 |
| **选择** | **② DDS 合成** |
| **量化依据** | 检测算法的验证需要心率在 **60~180 次/分可精确设定**。真实采集的心率不可控、个体差异大，且同一受试者难以复现特定心率，无法系统性地做边界测试 |
| **付出的代价** | 波形是"合成"的，不是真实患者的生理信号 |
| **为什么可接受** | 本项目定位是**信号处理系统**（DDS 生成 → 检测 → 计数 → 上传），核心价值在检测算法与软硬件协同；合成波形反而能**穷举各种心率工况**，可重复性远优于真实采集 |
| **答辩一句话** | "我们主动选择了 DDS 合成方案，因为**检测算法的验证需要心率可精确设定**——真实采集做不到这一点。合成波形让我们能把 60/72/120/180 各种工况都测一遍，这是可复现性的保证。" |

## D-02 · 32 位相位累加器 + 8 位相位截断

| 项 | 内容 |
|---|---|
| **备选方案** | ① 8 位累加器直接寻址（简单但分辨率差） ② 32 位累加器全用（ROM 需 4G 点，不可能） ③ **32 位累加 + 取高 8 位寻址** |
| **选择** | **③ 混合方案** |
| **量化依据** | 32 位累加在 100MHz 下的频率分辨率 = 100e6 / 2³² ≈ **0.023 Hz**；取高 8 位使 ROM 只需 **256 点 × 12bit = 3 Kbit**（而非 4G 点） |
| **付出的代价** | 引入相位量化误差（截断 24 位），表现为输出杂散 |
| **为什么可接受** | 截断 24 位对应杂散约 −48dB 量级，而心电信号的动态范围需求远低于此；且检测只关心"是否越过阈值 1200"，对微小杂散完全不敏感 |

## D-03 · 波形数据离线生成并存表，不在硬件里实时计算

| 项 | 内容 |
|---|---|
| **备选方案** | ① 在 FPGA 里用高斯函数发生器实时合成 P/QRS/T ② 用 Python 离线算好存入 ROM |
| **选择** | **② 离线生成 + ROM 查表** |
| **量化依据** | 实时合成 3 个高斯峰需要**指数运算与乘法**，会消耗大量 DSP/LUT；而查表只需 **1 块 ROM + 1 个地址**（实测仅占约 60 个 LUT 的查找表结构） |
| **付出的代价** | 波形形态在运行时不可修改 |
| **为什么可接受** | 本项目需要的是**固定形态的标准心电**，形态本身就是设计输入，不需要在线改变 |

## D-04 · 波形用 12 位偏移二进制存储（2048 = 基线）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 直接存有符号补码 ② **存偏移二进制，读取时减 2048** |
| **选择** | **② 偏移二进制** |
| **量化依据** | Verilog 的 `$readmemh` **只能读无符号十六进制**。偏移码让 `.mem` 数据文件**可直接人工阅读与核对**（基线一眼看出是 `800`） |
| **付出的代价** | 多一个 12 位减法器 |
| **为什么可接受** | 12 位减法器约十几个 LUT，而我们有 **98% 的 LUT 空闲**；换来的是数据文件可校验（实际验证时正是靠"第 0 点应为 0x800"确认了数据正确） |

# 二、V1（DDS 波形发生器）决策

## D-05 · 采样基准定为 250Hz，而不是按系统时钟计数

| 项 | 内容 |
|---|---|
| **备选方案** | ① 按系统时钟（100MHz）逐拍判断 ② **先分频出 250Hz 采样节拍再判断** |
| **选择** | **② 250Hz 采样节拍** |
| **量化依据** | 250Hz 是**真实心电监护仪的通行采样率**；R 波持续约 100ms，250Hz（4ms 间隔）可采到约 25 个点，足够定位峰值。若按 100MHz 计数：一次 RR 间期最长可达数亿个时钟，rr_count 需要 **26 位以上**，位宽与逻辑都浪费 |
| **付出的代价** | 需要额外的分频器（`tick_gen`），且检测器只在节拍到来时工作（引入了等待延迟） |
| **为什么可接受** | 分频器仅占约 19 个触发器；而换来的是**计数位宽从 26+ 位降到 16 位**、时间尺度与生理量直接对应（50 点 = 200ms 可一眼读懂） |
| **答辩一句话** | "我们把采样基准定在 250Hz，一是**对齐真实监护仪惯例**，二是让 RR 计数直接等于'采样点数'，**50 个点就是 200 毫秒**，生理含义一目了然。" |

# 三、V2（R 波检测）决策

## D-06 · 用固定阈值 1200，不用自适应阈值

| 项 | 内容 |
|---|---|
| **备选方案** | ① 自适应阈值（如动态跟踪峰值的 60%） ② **固定阈值** |
| **选择** | **② 固定阈值 1200** |
| **量化依据** | DDS 合成波形的幅度**完全已知**：R 波峰值 +2047、T 波 +614、P 波 +246。阈值取 1200 正好落在 T 波与 R 波之间，**理论上不可能误检或漏检** |
| **付出的代价** | 若波形幅度变化（真实 ECG 会），固定阈值会失效 |
| **为什么可接受** | 本项目信号源为 DDS 合成，幅度恒定为设计已知量；**引入自适应算法需要峰值跟踪、历史缓存与除法，复杂度与资源都显著上升，而收益为零** |

## D-07 · 增加 200ms 生理不响应期（blanking）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 只用阈值判断 ② **阈值 + 不响应期状态机** |
| **选择** | **② 阈值 + 不响应期** |
| **量化依据** | **若只用阈值**：T 波峰值 614 虽低于 1200，但 R 波本身有宽度，且**【若阈值取低或波形有噪声】，一次心跳会被多次计数**。更重要的是：本项目为覆盖不同心率，阈值必须低于 R 峰——而一旦阈值调低，T 波就会越线，**心率会直接翻倍**。不响应期设 50 点 × 4ms = **200ms**，正好覆盖 R→T 间隔 |
| **付出的代价** | 无法检出间距小于 200ms 的两次心跳（即心率高于 300 次/分） |
| **为什么可接受** | **生理上不可能**：人类心率上限约 220~250 次/分（RR ≥ 240ms）。200ms 的屏蔽期留了安全余量 |
| **答辩一句话** | "不响应期不是可选项而是**必须项**——因为我们要覆盖不同心率就必须调低阈值，而阈值一低 T 波就会越线，**心率会直接翻倍**。200ms 正好覆盖 R 到 T 的间隔，而生理上不可能有快于 300 次/分的心跳。" |

## D-08 · 心率除法放在 Python，硬件零 DSP 消耗

| 项 | 内容 |
|---|---|
| **备选方案** | ① 在 PL 里做除法，直接把 BPM 用寄存器送出 ② **PL 只输出 rr_count，除法交给 Python** |
| **选择** | **② 除法在 Python** |
| **量化依据** | ① 实测结果：本设计 **DSP 用量 = 0 / 220**。② 若在硬件做除法，需消耗 DSP48 或大量 LUT 构成除法器，并引入长组合路径压时序。③ 心率**每几秒才更新一次**，对实时性要求极低 |
| **付出的代价** | 系统无法脱离 Python 独立运行（必须 PS 参与才算完整） |
| **为什么可接受** | 本项目本身就是 **PS+PL 协同架构**，Python 是既定的组成部分；用软件承担"低频、复杂运算"正是软硬件划分的正例 |
| **答辩一句话** | "我们把除法放在 Python，**硬件 DSP 用量为 0**。理由是心率几秒才更新一次，实时性要求低；而硬件做除法要占 DSP 还会压时序——**这是典型的软硬件任务划分优化**。" |

## D-09 · RR 计数器位宽取 16 位

| 项 | 内容 |
|---|---|
| **备选方案** | ① 8 位 ② **16 位** ③ 32 位 |
| **选择** | **② 16 位** |
| **量化依据** | 250Hz 下，最慢心率按 20 次/分算：RR = 3 秒 = **750 个采样点**。16 位可表示到 65535，**余量 87 倍**；8 位仅到 255，**不够**（750 就溢出了） |
| **付出的代价** | 无（16 位对 FPGA 是极小的开销） |

# 四、V3（AXI 集成）决策

## D-10 · 选 AXI4-Lite，不用 AXI4-Full

| 项 | 内容 |
|---|---|
| **备选方案** | ① AXI4-Full（支持突发传输） ② **AXI4-Lite** ③ AXI4-Stream |
| **选择** | **② AXI4-Lite** |
| **量化依据** | 全部数据交互量 = **6 个寄存器 × 4 字节 = 24 字节**。AXI4-Full 的突发传输能力对大块数据搬运才有意义；Stream 无地址，不适合寄存器访问 |
| **付出的代价** | 无法做突发传输（每次只能读一个寄存器） |
| **为什么可接受** | 见 D-20 的定量分析：即便是 1024 点的波形读取，用寄存器间接方式也只需 **0.3ms**，远快于需求 |

## D-11 · 整条心电链全部使用 AXI 时钟域

| 项 | 内容 |
|---|---|
| **备选方案** | ① 检测逻辑用独立时钟（如板载 125MHz 晶振），经 CDC 与 AXI 交互 ② **全部使用 PS 提供的 `s00_axi_aclk`（100MHz）** |
| **选择** | **② 单一时钟域** |
| **量化依据** | 跨时钟域需要：双触发器同步器、异步 FIFO 或握手协议，且存在**亚稳态**风险（一种"数字电路的薛定谔态"，概率性出错，极难调试）。而本设计的时序余量 **WNS = +3.831ns（周期 10ns）**，100MHz 对它是轻载，**没有必须提频的理由** |
| **付出的代价** | PL 逻辑被绑定在 PS 的时钟上，不能独立于 PS 运行 |
| **为什么可接受** | 本系统本来就以 PS 为核心（Python 负责显示与运算），PL 独立运行没有意义；**用单时钟域换掉整个 CDC 风险类别，收益远大于代价** |

## D-12 · 把全部逻辑封装进一个 IP，对外只暴露 AXI

| 项 | 内容 |
|---|---|
| **备选方案** | ① 保留用户端口，在 Block Design 里手工连线 ② **全部封进 IP，对外只有 AXI** |
| **选择** | **② 单一 AXI 接口** |
| **量化依据** | 集成后 Block Design 只需 4 个方块、连接 1 条 AXI 总线；实测**一次 `Run Connection Automation` 即完成全部连线并通过验证** |
| **付出的代价** | IP 内部模块耦合，单独复用其中某一模块（如只要 DDS）需拆包 |
| **为什么可接受** | 本项目的 5 个模块是**一条完整的处理流水线**，天然应该整体复用；且对外接口越少，Block Design 出错概率越低 |

## D-13 · 用"寄存器穿透"方式传递自定义信号

| 项 | 内容 |
|---|---|
| **备选方案** | ① 为自定义信号定义新的 AXI 接口类型（需写 IP-XACT 描述） ② **在 AXI 从机上开 output/input 端口做穿透** |
| **选择** | **② 寄存器穿透**（`output reg_ftw` / `input reg_rr_count` / `input reg_wave_data`） |
| **量化依据** | 改动量：V3 阶段仅需 **2 个端口 + 1 行读选择器**；V4 再加 **2 个端口 + 1 行**。全程**不改动 IP 对外接口，因此无需重新打包、不改 Block Design、不改地址** |
| **付出的代价** | 每新增一个信号都要改端口列表与读选择器，可扩展性一般 |
| **为什么可接受** | 本项目自定义信号总共只有 4 个（ftw / rr_count / wave_addr / wave_data），**手工维护完全不成负担**；换来的是"零打包、零 BD 改动"的迭代速度 |

## D-14 · 小容量 ROM 用查找表实现，而非 Block RAM

| 项 | 内容 |
|---|---|
| **备选方案** | ① 用 Block Memory Generator IP 显式占用 BRAM ② **让综合器自行选择（实测走了查找表）** |
| **选择** | **② 查找表** |
| **量化依据** | 波形表 **256×12 = 3 Kbit**，而最小的一块 BRAM 是 **18 Kbit**——**利用率仅 17%，浪费 6 倍**。实测结果：**Block RAM 用量 = 0 / 140**，ROM 由查找表 + F7/F8 宽选择器实现（报告里 F7 Muxes=6、F8 Muxes=3 即为其痕迹） |
| **付出的代价** | 消耗约 60 个 LUT |
| **为什么可接受** | 全设计 LUT 用量仅 **554 / 53200 = 1.04%**，拿出 60 个（0.11%）换"不浪费 BRAM"完全值得；**BRAM 留给 V4 的波形缓冲更划算** |

## D-15 · 主动把 PS 的 `FCLK_CLK0` 从 50MHz 改为 100MHz

| 项 | 内容 |
|---|---|
| **备选方案** | ① 接受 PS 默认的 50MHz，把 IP 参数改成 50MHz ② **把 PS 时钟改成 100MHz，与 IP 参数对齐** |
| **选择** | **② 改时钟对齐** |
| **量化依据** | IP 内的采样分频按 `CLK_FREQ_HZ=100MHz` 推导：`TICK_DIV = 100e6/250 = 400000`。若实际时钟为 50MHz，真实采样率变成 `50e6/400000 = 125Hz`——**只有设计值的一半**，连带：不响应期从 200ms 变 400ms（会漏检）、rr_count 翻倍、**最终心率读数只有真值的一半**。⚠️ 这是**静默错误**（不报错） |
| **付出的代价** | 需要手工进入 PS 配置界面修改（容易漏） |
| **为什么可接受** | 100MHz 是 PYNQ 平台的通行值，改动只在一处；且改完后**时序仍有 38% 余量**（WNS +3.831ns / 10ns 周期） |

## D-16 · 不安装 PYNQ-Z2 板卡定义文件，改用通用器件 + 手动配置

| 项 | 内容 |
|---|---|
| **备选方案** | ① 安装 PYNQ-Z2 板卡文件（需联网下载） ② **选通用器件 `xc7z020clg400-1` + 手动配置 PS** |
| **选择** | **② 通用器件**（实测环境未安装板卡文件） |
| **量化依据** | 板卡文件提供两类信息：**(a) PL 引脚约束**（LED/按键/PMOD 引脚位置）——**本设计 PL 侧没有任何外部引脚**，完全用不到；**(b) PS 外设预设**（DDR 型号、MIO 分配）——而 PYNQ 从**预制的 SD 卡镜像启动**，PS 由启动镜像配置，**overlay 只配置 PL** |
| **付出的代价** | 设计里 PS 的 DDR 型号/MIO 分配取的是默认值，而非 PYNQ-Z2 的精确值 |
| **为什么可接受** | 不影响本设计的运行（PS 由启动镜像配置）；**若日后需要生成自己的 BOOT.BIN，或要驱动板上 LED，则必须补装板卡文件**——已记入待办 |

## D-17 · 工作区目录不做重排，竞赛提交包另建目录导出

| 项 | 内容 |
|---|---|
| **备选方案** | ① 直接把工作区重排成竞赛要求的目录结构 ② **工作区保持原样，另建 `submit/` 目录"复制导出"** |
| **选择** | **② 复制导出** |
| **量化依据** | 工作区存在**不可搬动的依赖**：① IP 的 `component.xml` 引用过 IP 目录外的路径 ② `.mem` 用绝对路径 `D:/ecg/vivado_src/...`。**任何一处搬动都会导致综合时找不到文件，而后果是静默的**（ROM 全 0、波形变直线） |
| **付出的代价** | 需要额外维护一个"导出"步骤，且要保证导出与工作区同步 |
| **为什么可接受** | "工作区服务于工具，提交包服务于评委"，两者结构诉求本就不同；**用一个导出步骤换取工作区的绝对安全**，是明显的正收益 |

## D-18 · IP 自包含化：HDL 移入 IP 内部 + 波形数据内嵌进源码

| 项 | 内容 |
|---|---|
| **备选方案** | ① 保持现状（引用 IP 外部文件 + `.mem` 绝对路径） ② 改相对路径 ③ **HDL 移入 IP + 数据内嵌进 Verilog** |
| **选择** | **③** |
| **量化依据** | ① 原状态：7 个源文件中 **5 个在 IP 目录外**，依赖 `edit_ecg_axi_v1_0.srcs\`；`.mem` 依赖绝对路径 → **换机器不可复现**（直接对应竞赛"可复现性"15 分）。② 改相对路径**不可行**：Vivado 综合 IP 时会把 HDL 复制到临时目录、在另一目录运行，`$readmemh` 找不到裸文件名，**失败是静默的**（即已知坑 A1）。③ 内嵌后：数据在源码里，**物理上不可能丢失** |
| **付出的代价** | `ecg_rom.v` 从 29 行变为 90 行（256 条赋值）；后续修改波形需重新生成；牺牲了"数据与代码分离"的整洁性 |
| **为什么可接受** | 改动前后 **HDL 内容零变化**（已验证两侧文件哈希一致），综合结果可预期不变；而换来的是"**拷到任何电脑都能综合**"+"**彻底消灭静默失效这一风险类别**"。安全性提升的价值远大于 60 行代码的代价 |

# 五、V4（波形缓冲与可视化）决策

## D-19 · 环形缓冲 1024 点 × 32 位

| 项 | 内容 |
|---|---|
| **备选方案** | ① 256 点（约 1 秒） ② **1024 点（约 4 秒）** ③ 4096 点（约 16 秒） |
| **选择** | **② 1024 点** |
| **量化依据** | 250Hz 下 1024 点 = **4.1 秒**；72 次/分时约 **5 个完整心跳**，P-QRS-T 形态可清晰辨认。存储量 1024×32bit = **32 Kbit = 2 块 BRAM18**，而当前 BRAM 用量为 **0 / 140** |
| **付出的代价** | 相对 256 点方案多占 24 Kbit |
| **为什么可接受** | 芯片有 **2520 Kbit** BRAM 空闲；用 32 Kbit 换"波形能看到 5 个心跳"，画面表现力提升显著 |
| **位宽选择** | 波形本身只有 12 位，但**存 32 位**（符号扩展）。理由：浪费 20 Kbit 换 Python **无需拆包**（直接读即有符号整数）。资源极度充裕时，**用资源换开发效率是正解** |

## D-20 · 波形读取用"寄存器间接读"，不用 AXI BRAM Controller + BMG IP ⭐

| 项 | 内容 |
|---|---|
| **备选方案** | ① **AXI BRAM Controller 官方 IP + Block Memory Generator**（可把 BRAM 映射为一段内存，整块读取） ② **两个寄存器：写索引 → 读数据** |
| **选择** | **② 寄存器间接读** |
| **量化依据** | ① 一次 AXI-Lite 寄存器访问约 **10~20 个时钟周期**，100MHz 下约 **100~200ns**。② 读 1024 点需要 1024 次"写索引 + 读数据" ≈ 2048 次访问 ≈ **0.3 毫秒**。③ 而波形是 **250Hz 的慢信号**（每点间隔 4ms）——**读取速度比采样速度快约 3000 倍** |
| **付出的代价** | 读取带宽上限低，不适合"高采样率 + 大数据量"场景；Python 侧需要循环读 1024 次 |
| **为什么可接受** | 本项目的采样率只有 250Hz，**0.3ms 的读取耗时完全无感**；换来的是：**不增加任何 IP、不改动 Block Design、不改地址分配、不需重新打包**——改动面最小，风险最低 |
| **答辩一句话** | **"我们评估过 AXI BRAM Controller 方案，但本项目的波形是 250Hz 的慢信号，用寄存器间接读取 1024 点只需 0.3 毫秒，已经比采样速度快 3000 倍。因此选择了不增加 IP、不改动 Block Design 的简化方案——这是有依据的取舍，不是能力不足。"** |

## D-21 · 复用 AXI 从机的空闲寄存器槽，不新增寄存器

| 项 | 内容 |
|---|---|
| **备选方案** | ① 重新生成 IP，把寄存器数从 6 个扩到 8 个 ② **复用现有空槽 0x04 与 0x0C** |
| **选择** | **② 复用空槽** |
| **量化依据** | 原设计的 6 个寄存器中，`slv_reg1`(0x04) 与 `slv_reg3`(0x0C) **一直是空槽**——综合日志已证明这一点：`slv_reg2_reg`/`slv_reg5_reg` 被作为死逻辑删除。V4 需要恰好 2 个新寄存器，**数量正好吻合** |
| **付出的代价** | 无（原本就是未使用的资源） |
| **为什么可接受** | 复用空槽意味着**寄存器数量不变 → IP 接口不变 → 无需重新打包 → Block Design 与地址分配全部不动** |

# 六、工程与流程决策

## D-22 · 仿真采用 1.25MHz 缩放时钟（而非 100MHz 全速）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 按 100MHz 全速仿真 ② **时钟缩放 80 倍（1.25MHz）+ FTW 同步缩放** |
| **选择** | **② 缩放仿真** |
| **量化依据** | 一次心跳（72BPM）需 0.83 秒仿真时间；100MHz 下是 **8300 万个时钟周期**——仿真时间与内存都不可接受。缩放到 1.25MHz 后仅需 **约 104 万个周期**，**快 80 倍**，且波形形态与检测行为**完全等价** |
| **付出的代价** | 需要设计全面参数化（时钟频率、分频值、FTW 都必须可推导），增加了设计复杂度 |
| **为什么可接受** | 参数化本身就是**良好的设计实践**（不同硬件配置可复用）；且该参数化在 V3 直接带来收益——IP 的 `CLK_FREQ_HZ` 作为参数暴露后，Block Design 里自动带出 100MHz 的默认值 |

## D-23 · 设计全面参数化（时钟/采样率/阈值/不响应期/表深）

| 项 | 内容 |
|---|---|
| **备选方案** | ① 所有常量写死在代码里 ② **全部做成模块参数** |
| **选择** | **② 参数化** |
| **量化依据** | 实测收益：综合/实现的资源与行为**完全不变**（LUT 从 645→554 的下降来自物理优化，与参数化无关）；而在 Block Design 中，Vivado **自动读出了 5 个参数的默认值**（`CLK_FREQ_HZ=100000000`、`SAMPLE_FREQ=250`、`THRESHOLD=1200`、`BLANK_LEN=50`、`ROM_AW=8`），**无需手工填写** |
| **付出的代价** | 参数沿模块层次传递时容易出现"**透传覆盖**"问题——曾踩坑：`dds_ecg` 把 `MEM_FILE` 透传给 `ecg_rom`，只改下层默认值会被上层覆盖（见踩坑 A2） |
| **为什么可接受** | 参数化让"仿真用慢时钟、上板用快时钟"成为**改一个参数**的事；踩坑已通过"参数链逐层检查"的规范规避并记录在案 |
