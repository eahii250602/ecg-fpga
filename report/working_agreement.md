# 协作约定（与 AI 助手）

> 本文件记录我们约定的工作方式。**助手在每次归档时机应主动查阅并执行本约定，不需要用户提醒。**

---

## 1. 操作分工（硬性规则）

| 场景 | 谁做 | 形式 |
|---|---|---|
| **Vivado / 板子 / 软件 的所有操作** | **用户手动** | 助手给出：**点哪里 → 弹出什么 → 填什么 → 应看到什么 → 出错怎么判断** |
| **写代码 / 改代码** | 助手生成 | 助手**逐行讲解**原理，用户自己粘贴 |
| **纯重复劳动**（批量复制、改名、归档文件） | 助手代做 | **助手先声明要做什么，再执行** |
| **读文件核对**（验证用户的操作结果） | 助手 | 只读，不改动 |

---

## 2. 每一步的交付标准

助手给出的每一步必须包含四样：

1. **操作**：具体点哪里、填什么
2. **原理**：为什么需要这一步、底层发生了什么
3. **预期现象**：做对了会看到什么
4. **出错判断**：症状 → 原因 → 处理

---

## 2.5 核对与指令规则（**强制；违反即视为重大失误**）

> **缘起**：2026-10-07 发生一次「假核对」事故——助手把一条**磁盘上并不存在**的代码写成
> "✅ 已核对通过"，导致一个静默失效的 bug（`reg_wave_addr` 无驱动）一路带到综合阶段，
> 最后是被 Vivado 日志的 `Synth 8-3848` 警告抓住的。

### 助手【下指令】时必须遵守

| # | 规则 |
|---|---|
| **I1** | **一条消息最多给 3 项改动**；超过就拆成多条消息（长指令本身提高漏项概率） |
| **I2** | 每项改动**独立编号**，并给出**唯一搜索锚点**（例如"全文唯一一处 `assign reg_ftw`"） |
| **I3** | 给完指令后，助手**自己先列一份"待核对清单"**（哪几项、各自搜什么关键字） |
| **I4** | 用户回报完成后，**逐项搜索并引用行号**，**一项都不许跳** |

### 助手【读文件核对】时必须遵守

| # | 规则 |
|---|---|
| **R1** | **每条结论必须附 grep/read 输出的原文行号**。没有行号 = 不许下结论 |
| **R2** | **某项未出现在输出里时，必须明确写 `❌ 未找到`**。**严禁因为"我下过指令"就推断"已存在"** |
| **R3** | **要核对 N 项，就出示 N 条证据**；证据不足时明写"**无法确认**" |
| **R4** | 核对**只认磁盘上的字节**，不认记忆、不认推断、不认"应该" |
| **R5** | 不确定的项宁可标"**待确认**"，**绝不标 ✅** |

### 一句话原则

> **★ 没有原文行号背书的"✅"，是假的 ✅。**
> **★ 工具（综合器 / DRC / 日志）不会撒谎；人工核对会。**

## 2.6 命令行必须逐条讲解（**2026-10-23 新增；用户要求学习常用命令**）

> **缘起**：用户明确要求——"**你之后给我的所有命令行代码都必须解释含义，我刚学一下常用语句们，不要直接甩给我代码**"。
> 目的不是"抄完能跑"，而是**在实操中学会常用命令**。

### 规则

| # | 规则 |
|---|---|
| **C1** | **每一条命令都必须讲解**。只给代码不解释 = 违反约定 |
| **C2** | 讲解必须含三层：<br>① **命令名**是什么工具（干什么用）<br>② **每个选项**（`-l` `-h` `-v` `-f` …）的含义<br>③ **每个参数 / 特殊符号**（`>` `>>` `2>&1` `2>/dev/null` `\|` `&` `\` …）的含义 |
| **C3** | 先讲 **`命令 选项 参数`** 的通用骨架，再讲本条的具体填法（让人能迁移到别的命令） |
| **C4** | 涉及**危险操作**（`rm` / `cp` 覆盖 / `>` 覆盖）时，必须**醒目标出**并说明后果 |
| **C5** | 新命令若通用性强，**点出可复用的模式**（例：`ls -lh` 这个组合到处都能用） |
| **C6** | 助手**自己执行**的命令（PowerShell / Vivado）若涉及用户需理解的动作，同样要说明在做什么 |

### 一句话原则

> **★ 只给代码不讲解 = 违反约定。用户要的是"学会"，不是"抄完"。**

## 3. 归档规则（**助手主动执行，不等用户提醒**）

### 触发时机

| # | 触发条件 |
|---|---|
| 1 | 每完成一个阶段成果（综合完成、实现完成、比特流生成、仿真通过、上板通过） |
| 2 | 每完成一个 V4 子任务（BRAM 加入、BD 修改、综合通过…） |
| 3 | 每次踩坑并修复之后 |
| 4 | 每完成一个重要实验（仿真 / 上板），含截图 |
| 5 | 开始新阶段**之前**，回头检查上一阶段材料是否已归档（补漏） |
| 6 | 长对话告一段落 / 用户要离开较长时间之前 |

### 每次归档，助手执行这五件事

1. 把生成的报告、截图复制进 `report/`（或 `report/images/`）
2. 在 `report/progress.md` 追加一行记录
3. 若本次有踩坑，写进 `skill/pitfalls.md`
4. **若本次做出了新的设计决策 / 方案权衡，追加进 `report/design_decisions.md`**
5. **先声明"现在是归档时机，我要做这几件事"，再执行**

## 3.5 生成物缓存与「改动后必须重建」规则（**2026-10-07 事故后新增**）

### 事故经过

修复 `hdl/ecg_axi_slave_lite_v1_0_S00_AXI.v` 后重新综合，警告 `Synth 8-3848`
（`reg_wave_addr` 无驱动）**依旧存在**。排查发现：

```
   源文件修改时间  22:28:55  （含修复）
   综合缓存副本    22:10:41  （★ 比源文件旧 18 分钟，不含修复）
   runme.log       22:32:59  （综合确实重跑了）
        ↓
   Vivado 重新跑了综合，但用的是【缓存里的旧副本】，没有同步源文件
```

### 规则

| # | 规则 |
|---|---|
| **G1** | **改完任何 IP 源码后，必须强制重建生成物缓存**：<br>`File → Close Project` → **完全退出 Vivado** → 删除 `<project>.gen` → 重开工程 → 再综合 |
| **G2** | **重建后先验证缓存，再看综合结果**：检查 `.gen\...\ipshared\*\hdl\<改过的文件>` 的**修改时间晚于源文件**，**且内容含改动** |
| **G3** | **`.gen` 是生成物目录**：可安全删除，不会丢源文件/BD/约束；**删除前必须确认 Vivado 已完全退出**（否则会删一半留一半） |
| **G4** | **里程碑构建完成时，归档 `.bit` + `.hwh`**（不只是报告）——它们可再生，但归档一份才能保证"能跑的版本"不丢失 |
| **G5** | 设计一改动，Vivado 会**清空实现运行目录**（`impl_1`）→ 旧比特流失效属正常，但要**先确认源文件完好** |

### 已知疑点（未证实，故采取保守策略）

```
   component.xml 里【有】校验值的文件：ecg_axi.v、tick_gen.v   → 改动【能】被察觉
   component.xml 里【没有】校验值的文件：其余 5 个              → 改动【不能】被察觉
        ↓
   机制未证实，因此 G1 采取"一律强制重建"的保守策略
```
