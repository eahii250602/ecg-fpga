# 一、硬件加速

## 1.1 现状诊断（附证据）

```
   证据：ecg_axi.v L124-130（tick_gen 分频 400000 → 250Hz）
         L133（阈值比较 assign above = ecg_wave > THRESHOLD）
        ↓
   ★ 全链路的"计算量" = 每 4 ms 做一次 12 位比较
   ★ 100 MHz 的 DDS 生成能力只用掉了 0.00025%
   ★ 【软件轻松胜任】→ 没有任何"非硬件不可"的论证
```

**结论**：当前项目**无法证明"硬件加速"**，因为负载太小。

---

## 1.2 原始方案 v1（偏薄，需要深化）

> 原方案：*"1 MHz 实时 FIR + 实测抖动对比"*

### ⚠️ 弱点分析

| # | 弱点 |
|---|---|
| 1 | **FIR 太简单**：32 阶、1 MHz → 32 M MAC/s，1 个 DSP 时间复用就够 → 加速比不够震撼 |
| 2 | **"抖动对比"是论证方法，不是功能** → 容易被看作"为了写报告而做的实验" |
| 3 | **没有"非做硬件不可"的硬指标** → 只是"软件慢一点"，不是"软件做不到" |
| 4 | **单通道**，白白浪费 FPGA 的并行本质 |
| 5 | 与"多通道/多模态"的真实需求脱节 |

---

## 1.3 深化方案：四层递进（L1 → L4）

### L1（保底）：多通道并行实时 FIR + 实时可调度性论证

**功能**：
```
   N 通道并行实时 FIR 滤波流水线（N = 1 / 4 / 12 / 32 可配）
        ↓
   依据：临床 12 导联是标准；HD-EMG 阵列 64~256 通道
```

**论证升级**（不只是"实测抖动"，而是**实时系统理论**）：
```
   ① 吞吐率对比
        硬件：N 通道 × 1 MHz × 32 阶 = 32N M MAC/s（确定性）
        软件：Python 单点约 3.2 µs（实测）→ 12 通道需 38 µs/采样集
        采样周期 1 µs → 【38 倍差距】
   
   ② ★ 可调度性分析（实时系统理论）
        T_sample = 1 µs
        软件 WCET（最坏执行时间）≈ 3.2 µs，且 Linux 非实时 → WCET【无界】
        → 3.2 µs > 1 µs → 【必然错过截止期】(deadline miss)
        → 数学上证明软件方案不可行，而不只是"比较慢"
   
   ③ 确定性对比
        硬件：固定 N 个时钟周期（可数出来）
        软件：P50 / P99 / max 抖动分布（实测直方图）
```

**产出**：吞吐对比表 + 抖动直方图 + 可调度性分析（含公式）

---

### L2（加强）：完整 Pan-Tompkins **数据流流水线**（II = 1）

**功能**：
```
   抽取/重采样 → 基线去除(高通) → 50Hz 陷波 → 带通
   → 微分 → 平方 → 移动窗积分 → 自适应双阈值 → 峰值定位
```

**★ 关键设计成就：数据流架构 + 深度流水线**
```
   每个时钟周期产出一个结果 → 【II = 1 (Initiation Interval = 1)】
        ↓
   对比：
     软件：逐点循环，每点几百条指令
     硬件：数据流，数据流过即算，每周期一点
        ↓
   ★ 这是【体系结构级】的设计成就，不是"实现了一个滤波器"
```

**明确指标**：端到端延迟（从 R 波出现到检出，多少个时钟周期）+ 吞吐率

---

### L3（深化）：★ 面积-吞吐-精度-功耗 **四维权衡实验**

**★ 这才是硬件加速的精髓：不是"越快越好"，而是权衡**

```
   ┌──────────────┬────────┬────────┬────────┬────────┐
   │ 架构变体      │ 资源    │ 吞吐    │ 精度    │ 能效   │
   ├──────────────┼────────┼────────┼────────┼────────┤
   │ 全并行 (64 PE)│ 高      │ 极高    │ 高      │ 中     │
   │ 部分并行 (8)  │ 中      │ 高      │ 高      │ 高     │
   │ 全串行 (1)    │ 低      │ 中      │ 高      │ 极高   │
   │ 定点 8-bit    │ 低      │ 高      │ 略降    │ 极高   │
   │ 定点 4-bit    │ 极低    │ 极高    │ 降      │ 极高   │
   └──────────────┴────────┴────────┴────────┴────────┘
        ↓
   ★★ 产出 4~5 个架构版本 × 实测资源/吞吐/精度 → 真正的"优化对比表"
   ★ 直接对应"性能与资源优化效果 20 分"
   ★ 而且适合作为"大模型协作"的选题（让 LLM 辅助架构选型）
```

**扩展到 L4（冲刺）：★★★ QCNN 加速器**
```
   1D-CNN 心律失常分类，4-bit 量化
     · 脉动阵列 / MAC 阵列
     · 权重复用 + 数据复用（降低带宽压力）
     · 量化：4-bit → 乘法变查表
     · 片上存储层次：寄存器 → BRAM → DDR
        ↓
   ★ 指标：GOPS、GOPS/W、PE 利用率、带宽需求、推理延迟、精度
   ★ 这是"硬件加速"的完整形态，也是【端侧 AI】这个最大科技热点的落地
```

## 1.4 ★ 与接口设计的交汇（联合命题）

```
   ★★★ 一条完整的数据通路：
   
   [多通道采集] → [接口] → [加速处理] → [协议传输] → [显示/存储]
        │            │          │            │
        │            │          │            └─ 自定协议 / AXI-Stream / DMA
        │            │          └─ 多通道并行 DSP + QCNN

      全部在【一条数据流水线】上体现
        ↓
   ★★★ 这是"系统集成"的最高形态：
        不是功能堆砌，而是【一条完整数据通路的端到端优化】
```

# 二、接口设计

## 2.1 现状诊断（附证据）

| 现状 | 证据 |
|---|---|
| AXI4-Lite 握手逻辑是 **Xilinx 模板** | `ecg_axi_slave_lite_v1_0_S00_AXI.v` |
| 我们的贡献只有寄存器映射 + 读选择器 + 信号穿透 | L222-264（写译码）、L326（读选择器）、L329（穿透） |
| **从未做过协议级验证** | 待办清单"写 AXI 测试台"仍是 ⬜ |
| **没有接口文档** | 寄存器映射只在代码注释里 |
| **协议规范层面完全没碰** | `BRESP`/`RRESP` 永远是 `OKAY`，越界静默忽略 |

---

## 2.2 原始方案 v1（偏薄，需要深化）

> 原方案：*"自写 UART（同时补状态机 + I/O 时序约束）"*

### ⚠️ 弱点分析

| # | 弱点 |
|---|---|
| 1 | **UART 是教科书级接口**，没有设计空间（帧格式基本固定） |
| 2 | 只是"**多了一种协议**"，不体现**协议设计能力** |
| 3 | 与"接口设计"考察点的深层要求不匹配：<br>深层要求 = 能**设计**协议 / 能**处理错误** / 能做**协议转换** |
| 4 | 没有"**验证协议正确性**"的环节 |
| 5 | 没有连接**真实的、有难度的器件** |

---

## 2.3 深化方案：四层递进（L1 → L4）

### L1（保底）：多协议主机 + 完整接口文档 + 协议栈分层设计

```
   自写协议主机（不用 Xilinx IP）：
     · SPI 主机（驱动 DAC / ADC / OLED）
     · I2C 主机（驱动 OLED / 传感器）—— 含 ACK/NACK、开漏三态
     · UART（含波特率精度量化分析）
     · 正交解码（旋转编码器）
        ↓
   + AXI 规范化：响应码 OKAY/DECERR/SLVERR + 自动递增读 + 事务/错误计数器
   + 接口文档：寄存器映射表 / 访问协议 / 时序约定 / 数据类型 / ★边界行为
   + 协议栈分层文档（物理层→应用层）
```

---

### L2（加强）：★ 设计一个完整的分层自定义协议

**不是"实现 UART"，而是"设计一套协议"**

```
   ┌──────────────────────────────────────────────────┐
   │ 生理信号流协议（PSSP）— 自定                       │
   ├──────────────────────────────────────────────────┤
   │ 应用层 │ 波形流 / 事件通知 / 参数配置 / 诊断信息     │
   │ 会话层 │ 连接建立 · 心跳保活 · 优雅断开              │
   │ 传输层 │ 序号 · ACK/NACK · 超时重传 · 流控(滑动窗口) │
   │ 网络层 │ 设备地址 · 消息类型                        │
   │ 链路层 │ 帧同步(0xAA55) · 字节转义 · CRC16           │
   │ 物理层 │ RS-485 半双工 / SPI 高速 / UART             │
   └──────────────────────────────────────────────────┘
        ↓
   ★★ 每一层都有【设计决策 + 理由】（为什么用 CRC16 不用累加和？
       为什么需要字节转义？窗口大小怎么定？）
        ↓
   ★ 产出：协议规范文档 + 收发状态机 + 测试台
```

---

### L3（深化）：★★ 协议一致性测试套件 + 协议转换桥 + 接口自诊断

**① 协议一致性测试套件（协议工程的闭环）**
```
   正常路径测试
   异常注入：位错误 / 帧丢失 / 重复帧 / 乱序 / 超长帧 / 零长度帧
   边界：最大帧长 / 全 0 / 全 1
   压力：满窗口 / 连续背靠背
        ↓
   统计：通过率 · 错误检测率 · 故障恢复时间
        ↓
   ★★★ 完整闭环：设计 → 实现 → 验证 → 一致性测试
```

**② 协议转换桥（最能体现接口设计深度）**
```
   AXI4-Lite      → 自定义寄存器总线（连接多个子模块）
   AXI4-Stream    → 寄存器（让 Python 能读流数据）
   自定义协议      → AXI4-Stream（外设数据进 PL 处理链）
        ↓
   ★ 协议转换是接口设计的高阶能力
```

**③ 接口可观测性与自诊断**
```
   每个接口的错误计数器（CRC错 / 超时 / 溢出 / 帧错）
   链路质量统计（误码率估计、重传率）
   ★ 片上轻量逻辑分析仪（自建 ILA）：捕获协议时序用于调试
        ↓
   ★ 既补"接口协议"，又补"性能数据"，还提升可调试性
```

---

### L4（冲刺）：★★★ 接入真实医疗级器件

**接口的价值在于"连接"。接真实的、有难度的器件：**

| 候选器件 | 接口 | 难度与价值 |
|---|---|---|
| **★ ADS1292 / ADS1299**（TI 生物电前端 AFE） | SPI | **最高**：几十个配置寄存器 + 上电序列 + DRDY 中断 + 多通道数据读取；**让项目从"纯合成"变成"能接真实电极"** |
| **microSD 卡** | SPI | 高：FAT32 文件系统 + 长时程数据存储 |
| MAX30102（PPG 血氧/脉搏） | I2C | 中：多模态扩展 |
| MPU6050（IMU） | I2C | 中：运动伪影补偿 |
| 以太网 PHY | RGMII | 高：高速数据传输 |

**★ ADS1292 是最有价值的**：它是**真正的医疗级器件**，其配置流程（上电序列 → 寄存器配置 → 数据就绪中断 → 连续采样）是**真实的接口设计挑战**。

---

### 补充：★ 时间同步协议（多传感器系统的关键）

```
   多传感器融合的核心难点 = 【时间对齐】
     · 硬件时间戳（每个采样带 64 位计数器值）
     · 跨传感器公共时基
     · 或实现 PTP / IEEE1588 的简化版
        ↓
   ★ 这是真实工业/医疗系统的关键技术
```

# 三、两项的联合命题（★ 建议优先考虑）

```
   【多通道生物电信号的实时采集-处理-传输流水线设计】

   ★★★ 这不是"加功能"，是【一次架构级的项目升级】
```
