## 一、动机

当前设计实测资源占用为 LUT 3.36%、FF 2.37%、BRAM 1.07%、DSP 7.73%。
就"单导联滤波 + R 波检测"而言该占用合理，但对 Zynq-7020 而言**功能覆盖面偏窄**：
缺少多导联、缺少对工频频率漂移的自适应能力、缺少硬件级信号质量评估、
缺少硬件级 HRV 统计、且采样时刻仍由软件决定。

本方案的目标不是提高占用率本身，而是**在无冗余逻辑的前提下扩展功能边界**，
使资源规模与功能规模匹配，并消除"采样时刻由软件决定"这一结构性弱点。

## 三、为何每一项都是"优化使用"而非堆砌

| 模块 | 资源效率依据 |
|---|---|
| ① 三链并行 | 复用同一模块参数化例化，无新增设计成本 |
| ② 导联合成 | 仅加法器与右移一位（×0.5），**零 DSP**；6 个输出导联约 200 LUT |
| ③ 自适应 LMS | 每谐波每样本 1 乘 2 加（6 个 tap → 6 DSP），优于重做可变系数 biquad |
| ④ Goertzel SQI | 单频 DFT，1 个乘法器算出一个频点；相比 256 点 FFT（15~20 DSP）节省约 3 倍 |
| ⑤ HRV 硬件 | 仅累加一阶/二阶矩（4 个累加器），无需存储完整 RR 序列 |
| ⑥ DMA | 其价值不在吞吐量而在时序解耦（§六），判据为抖动与 CPU 占用，非带宽 |

## 六、AXI DMA：已决定采用

### 6.1 结论变化的原因

此前结论为"原始波形 500 B/s，DMA 固定开销高于吞吐收益"。
该判断**仅计入吞吐量维度**，遗漏了更关键的第二个维度：**采样时刻的控制权**。

| 维度 | 现状（PS 忙等轮询） | DMA 环形缓冲 |
|---|---|---|
| 采样时刻决定方 | **软件循环** | 硬件时钟 |
| 抖动 | 3.9 ~ 57 µs（受 Linux 调度影响） | **< 16 ns** |
| CPU 占用 | 占满一核（忙等） | 约 0 |
| 连续采集时长 | 约 20 s（受内存限制） | 约 256 s（DDR 环形 64 k 样本） |

项目中已实测：`time.sleep(4ms)` 导致采样率偏差 **+5.70%**，使 50 Hz 陷波完全失效。
即便改用 `perf_counter` 忙等将均值误差压到 0.00%，其抖动仍由操作系统决定。
**只要采样时刻由软件决定，该结构性弱点就始终存在。**

### 6.2 具体方案

```
sample_tick (250 Hz, 硬件)
      │
      ▼
ecg_axi 新增 AXIS 主口：tdata = {sample[15:0]}, tvalid = sample_tick, tready ← DMA
      │
      ▼
AXI DMA（S2MM，循环模式，SIG 模式可选）
      │
      ▼
DDR 环形缓冲（64 k 样本 = 128 KB ≈ 256 秒）
      │
      ▼
PS 侧随时读取，不参与采样节拍
```

BD 变更：新增 AXI DMA IP，S2MM 侧接 `ecg_axi` 的 AXIS 主口，
M_AXI_S2MM 接 PS 的高性能口（HP），S_AXI_LITE 接 PS 的 GP 口。

### 6.3 验收判据（可测量，非主观）

| 项 | 判据 | 测量方式 |
|---|---|---|
| 采样抖动 | **< 16 ns**（一个时钟周期） | 硬件时间戳 / 由 FIFO 计数核对 |
| 丢点 | 60 秒连续采集 **0 丢点**（15000 样本） | 首尾计数差 vs 样本数 |
| CPU 占用 | **< 5%** | `top` 采样 60 秒 |
| 与寄存器读法一致性 | 同一段信号两种读法的数据**逐位相同** | 比较缓冲区内容 |

### 6.4 风险控制

DMA 涉及 BD 变更与新的时序路径，是全部模块中风险最高的一项。
控制措施：**单独一次重建**，不与功能模块合并；若失败则回退至 v5，
其余模块不受影响。

## 七、单导联三参数的集成路径

### 7.1 已完成（软件层，已验证）

`python/vitals.py` 已实现并通过注入验证：

| 参数 | 结果 | 判据 |
|---|---|---|
| HR | 71.97 BPM（真值 72） | R 峰 71/71 检出 |
| HRV | SDNN 26.9 ms、RMSSD 25.0 ms、pNN50 | 注入已知心率变异 |
| EDR 呼吸率 | 12→11.8 / 15→15.0 / 18→18.2 次/分 | 误差 < 0.5（实测最大 0.2） |

### 7.2 后续集成步骤

| 步骤 | 内容 | 依赖 |
|---|---|---|
| 1 | 将 `vitals.py` 的算法接入板端脚本，对板子采集的数据实时计算三参数 | 无（可立即进行） |
| 2 | 若 DMA 落地：由 DDR 环形缓冲持续供数，三参数随时间连续输出 | ⑥ DMA |
| 3 | 硬件只承担 HR 与 HRV 的累加统计；**EDR 保留在 PS** | ⑤ HRV |

### 7.3 为何 EDR 不下沉到硬件

EDR 的关键步骤是「剔除 QRS-T 区间 + 线性插值」——该操作依赖对不连续区间的插值，
在硬件中实现代价高且收益低。

若强行以"0.05 Hz 高通 + 谱峰"实现，将重蹈 §5.1 的覆辙：
0.05 Hz 的极点半径更接近 1，定点实现的量化误差放大倍数比 0.5 Hz 高通更严重。
**故 EDR 保留在 PS，硬件只承担可定点化、可流水的部分。**
