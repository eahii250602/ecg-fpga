# 大模型协作记录

> 本文记录的不是"我提问、模型回答"，而是**我给模型立了什么规矩、这些规矩如何改变了它的输出、以及我如何用它推进一个我自己并不完全会的项目**。
>
> 所有引用的提示词均为本人原话，未做修饰。

---

## 一、协作模式：我要的不是代做

这个项目涉及 Verilog、Vivado 时序、定点数值、心电生理、模拟前端——**我没有一样是精通的**。

但我给自己定了一条底线：

> **模型可以替我写代码，但不能替我理解；可以给我答案，但必须让我能判断答案对不对。**

于是分工是：

| 我做 | 模型做 |
|---|---|
| 焊/接线、换卡、上电、量电压、贴电极 | 写 RTL / Python / Tcl |
| **判断一个方案值不值得做** | 给出方案与判据，并说明代价 |
| 把实测数据发回去，推翻它的结论 | 修正判断，并说明自己错在哪 |
| 决定项目的方向和优先级 | 执行，并在不认同的时候说出来 |

这也是为什么这份记录里**失败和纠错占了大量篇幅**——因为判断对错的权利在我手上，而判断的依据只能是数据。

## 二、我给模型立下的四条规矩

这四条不是模型主动给的，是我在协作中**一条一条逼出来的**。

### 规矩 1：先定性解释，再谈方案——不能上来就扔代码

**我说的话**：

> 「之后所有这些引入的专业核心新概念都要先讲解是什么，不然我不知道你在干嘛，记住之后都这样！」
>
> 「具体详细教 你上面说的主谓宾都不完整 看不懂」

**为什么提这个**：模型默认的毛病是"给一段能跑的代码 + 三行注释"。但我不知道 `TICK_DIV` 是什么、
不知道为什么要在 `A(1)≈0` 的反馈环里用四舍五入，**那段代码对我来说就是黑箱**。
黑箱能跑通一次，改一个参数就崩，而且崩了我不知道为什么。

**模型被逼出来的四段式**：

| 段 | 回答什么 |
|---|---|
| ① 是什么 | 概念的定义（例：Q2.14 是"用 14 位表示小数部分"的定点格式） |
| ② 生活类比 | 为什么这么设计（例：像用"厘米刻度"而不是"米刻度"量身高） |
| ③ 本项目里的具体数字 | 落到本项目的量（例：±2 的范围、分辨率 1/16384） |
| ④ 为什么用它 / 不用会怎样 | 代价与替代方案（例：用 Q1.15 会静默截断 −1.9823） |

**效果**：后面我能自己判断"这个系数会不会溢出"，而不是每次都要问。

---

### 规矩 2：代码要逐行讲，讲清"这一行在防什么"

**我说的话**：

> 「电阻接入不影响吗」（追问一个看似无关的细节）
>
> 「仔细思考慎重给答案」

**模型的转变**：

- **之前**：`(acc + 8192) >>> 14` 配一句"四舍五入"。
- **之后**：说明**为什么必须四舍五入**——纯截断对负数向下取整，产生负向直流偏置，
  而这个偏置会被 `A(1)=1.565e-4` 的反馈环放大，**最终发散并饱和到 −2048**。
  这不是"规范写法"，是**这个结构能不能活的必要条件**。

**效果**：代码注释从"这里做了什么"变成"**这里不这么做会死在哪**"。
`ecg_filt.v` 里每一处非常规写法都能追溯到一次实测失败。

---

### 规矩 3：任何设计先讨论"有没有必要"，再谈"怎么做"

**我说的话**：

> 「感觉没有太大用」
>
> 「skill先不搞，你那些都太鸡肋平庸了没有价值」
>
> 「且要是真正有意义的功能」
>
> 「之前的事情先做完……别用一个平庸毫无新意的项目结束这次比赛」

**模型的转变**：

| 模型原本要做的 | 我的评价 | 最后是否做 |
|---|---|---|
| 加 AXI DMA（因为清单里有） | 「500 B/s 数据配 DMA 是负优化」 | ❌ **不做，并在 README 里写明为什么不做** |
| 写 3 个 PYNQ Skill 包 | 「鸡肋平庸，没有价值」 | ⏸ 推迟（先做有技术含量的） |
| 把采样改成 `perf_counter` 忙等 | 「先说这个改动值多少」 | ✅ 做（因为换算了：采样率偏 5.7% → 陷波完全失效） |
| 加 SQI 信号质量指数 | 「没有基线对比就加上啊」 | 🔄 进行中 |

**效果**：模型开始**主动给出"不做什么"的理由**，而不是罗列能做的功能。
这些"不做"的判断后来原样写进了 README 第 4.9 节。

---

### 规矩 4：必须经常反思总结，并且写成文件

**我说的话**：

> 「一定一定养成习惯，做好记录」

**模型的响应**：`report/WORKLOG.md` 从几百行写到 **50 KB**，每条任务固定四栏：

```
做了什么 | 为什么 | 证据 | 思维亮点
```

并且要求：**每次出错都要留下"当时怎么想的、错在哪、下次靠什么避免"**。

**这不是流水账**——它是项目里唯一能回答"你当时为什么这么决定"的东西。
答辩时被问"这个参数怎么来的"，答案是翻到对应日志行。

## 三、我如何"互相促进"：六个真实交锋

规矩是静态的，真正推动项目的是**我不断质疑、模型被迫修正**的过程。

### 交锋 1：「为什么第 12 列就是地？谁规定的？」

模型当时给了一张接线图，写着"把 GND 接到第 12 列"。

我追问：**第 12 列为什么是地？谁规定的？第 13 列为什么不是？**

模型的原始回答是"第 12 列空着方便"。这个回答是**操作层面的敷衍**。

被追问后，它才讲出真正的东西：

> 面包板本身不带电、没有"地"。**你把 PYNQ 的 GND 接到哪一列，哪一列才变成地。**
> 规则只有一条：所有需要接地的点，最后必须落在**同一个电气节点**上。

**我的收获**：我不是记住"接第 12 列"，而是理解了"地"是我定义的，只要**一致性**成立即可。
后来我自己判断出了"用边上的 `−` 长轨更好，因为一整条都通"，这是模型没主动说的。

### 交锋 2：「你这个明明是接到 3v3 母线而不是 PYNQ 的 3v3」

模型画的图里有一条"3.3V 母线"，但**没画它从哪来**。我指出这是自相矛盾。

模型的反应是承认"图没画完"，并在图上补了来源标注：

> `← 从 PYNQ 板 3V3 排针引出（面包板上 = 插了它的那一列）`

**我的收获**：示意图必须**闭合**——每个"网络"都要能追溯到物理来源。
后来我把这个要求迁移到了 README 的架构图（PS 和 PL 各自的数据来源都标注清楚）。

### 交锋 3：「感觉没有太大用」

模型花了两小时做"主机样本通道"，讲了一堆好处。我直接说：**感觉没太大用。**

模型被迫重新评估，承认：

> 这 5 行 RTL **不改变系统能做、不能做的事**。它是"接口"，不是"能力"。
> 真正有价值的是同一轮里的**时基改造**——它把硬件陷波从"失效"救回"有效"。

**我的收获**：判断一个改动值不值，要问"**它改变了哪个可测量的指标**"，
而不是"它增加了什么功能"。

### 交锋 4：「知道很常规那就赶紧加创新点」

我在看完评分表后指出：**这个项目本质是"又一个心电 + 陷波 + Pan-Tompkins"，创新性 30 分是最大缺口。**

模型的反应是列了 A/B/C 几个方案（自适应陷波 / SQI / 边缘 AI）。
我否掉了"边缘 AI"（3 天做不完）和"自适应陷波"（风险高），
选择了 **SQI + EDR**——因为：

- 我们**自己实测证明了**"采到的数据不可信"，这就是 SQI 最好的动机；
- EDR 能**从同一条导联里多榨出一个生理参数**，是真正的应用价值。

**我的收获**：创新不是"加新算法"，而是**把自己踩过的坑变成别人需要的能力**。

### 交锋 5：「我根本没有连 AD 模块，只连了板子」

模型根据"VP 只有 104 码"推断"AD8232 可能断线了，去检查 3.3V/GND"。

我告诉它：**模块压根没接**。

模型随即修正了判断，并把 WORKLOG 里那条"⚠ 发现的异常"改成了"B 段说明（已澄清）"。

**我的收获**：**模型的推断再合理，也要用我的现场事实去校验。**
我不在现场的时候，它会给出听起来很专业但其实错的诊断。

### 交锋 6：「你给的决策有的很笨，一定要展现思维深度」

第一版 README 的"关键设计决策"列了 8 条，其中"IIR 比 FIR 省资源""PL 内建注入器"这类是**教科书常识**。

我要求：**删掉笨的，只留真正有取舍的。而且不要只写最后几个环节，前面那么多环节也要回想。**

模型重写成 9 条，每条都是「**冲突 → 证据 → 决策 → 为什么这是对的**」，
并且覆盖了从项目早期（放弃 0.5 Hz 数字高通）到最近（为何不加 DMA）的完整时间线。

**我的收获**：**"做了什么"不值钱，"为什么没做另一个"才值钱。**

## 四、我给模型提的"高要求"，具体长什么样

除了上面四条规矩，我在不同阶段还提过这些硬性要求：

| 阶段 | 我的要求 | 模型必须交付什么 |
|---|---|---|
| 概念讲解 | 「先讲是什么」 | 四段式（定义/类比/本项目的数/为什么用它） |
| 硬件接线 | 「我不懂怎么接线」「主谓宾都不完整看不懂」 | 图示 + 逐孔说明 + 万用表验证步骤 |
| 工程决策 | 「先说这个改动值多少」 | 换算成可测量指标，不能只说"更好" |
| 验证 | 「仔细思考慎重给答案」 | 判据 + 失败条件 + 被我推翻后的修正 |
| 文档 | 「整个 README 读完不知道干了啥」 | 问题驱动叙述，不是结果罗列 |
| 复盘 | 「一定一定养成习惯，做好记录」 | WORKLOG 四栏 + 每次纠错留痕 |

## 五、我不只是提要求，我自己在学、在动手

这一节写我自己——因为**如果全是模型在干，这个项目不成立**。

### 我亲自做的事

| 事 | 说明 |
|---|---|
| 硬件接线 | 面包板、分压电阻、杜邦线、J5 排针，全部自己接 |
| 换卡与部署 | 每次重建后自己关机、拔卡、拷文件、核对 MD5、上电 |
| 上板实测 | 几十条命令全部自己粘贴、自己跑、自己看输出 |
| 人体实验 | 电极贴附、姿势控制，全部自己做 |
| **每一次质疑** | 本文件第三节的六个交锋，全是我先开口 |

### 我主动搞懂的原理（不是模型灌给我的）

| 问题 | 我为什么问 | 得到的理解 |
|---|---|---|
| "第 12 列为什么是地？" | 不接受"就这样接" | 地是我定义的，关键是**同一个节点** |
| "能不能用 `+` 长轨当 3.3V？" | 想自己优化接线 | 可以，但**长轨本身不带电**，要先把源接上去 |
| "电阻接入不影响吗？" | 担心测量被干扰 | 1.27 kΩ 对 GΩ 级输入的影响是 **1.27 纳伏** |
| "这个检测用到了之前所有成果吗？" | 想确认项目是不是"拼凑" | 只用到约 40%，硬件滤波和 PT 当时并未参与真实数据 |
| "我这个项目算成功吗？" | 要一个**不吹的**答案 | "成功但未完成"，并给出缺口的准确位置 |

### 我给自己的原则

> **看不懂的步骤不做。** 如果模型给的操作我说不清"这一步在干什么、失败会长什么样"，我就要求它重讲，
> 而不是照着敲。这拖慢了进度，但换来的是——**板子出问题时我知道该看哪里**。

## 七、协作的边界：哪些事模型替代不了

这一节是给后来者的提醒，也是我自己的总结。

| 事 | 为什么替代不了 |
|---|---|
| **硬件是否真的接对** | 模型只能看照片，而照片分辨率有限；最终只能靠万用表/实测数据 |
| **一个方案值不值得做** | 模型倾向于"多做"，因为它不需要为时间负责；取舍必须我来 |
| **身体上的实验** | 安全、感受、是否继续，只有我能判断 |
| **承认"这个结论不成立"** | 模型会顺着我的假设编解释；必须我用数据否决它 |
| **项目的方向与取舍** | 30 分的创新性该往哪投，是人的判断 |

### 一条最实用的经验

> **模型最擅长的是"给出可被证伪的假设"，最不擅长的是"承认自己错了"。**
>
> 所以我的用法是：**让它给假设，我用数据去杀。**
> 本轮被数据杀掉的假设包括：插座短路、芯片损坏、注入器幅度减半、缓冲未刷新、
> 自相关找到心跳、周期扫描找到心电——**六个**。
> 每一个被否掉，项目就往前走一步。
