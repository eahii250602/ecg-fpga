# 大模型协作记录

## 引言

本项目周期约四周，覆盖 RTL 设计、时序收敛、板级调试与真实生理信号采集，由单人完成。

在这一约束下引入大模型，目的不是替代判断，而是**在保持判断权归属本人的前提下扩大产出规模**。
协作能否成立，取决于本人能否对模型输出施加**明确、可执行、可核查的约束**——
否则模型会以高置信度交付未经论证的结论，而这一代价在硬件项目中不可承受。

本文记录这些约束的形成过程、它们如何改变模型的输出形态，以及由此产生的可核查结果。

---

## 一、协作的基本形式：约束先于产出

项目第二日即形成成文文件 `report/working_agreement.md`（下称《协作约定》），
以编号规则的形式规定协作方式，而非依赖临场沟通。其结构包括：

| 章节 | 内容 | 约束对象 |
|---|---|---|
| §1 | 操作分工 | 物理操作一律由本人执行，模型不得代劳 |
| §2 | 每一步的交付标准 | 须含「操作 / 原理 / 预期现象 / 出错判断」四项 |
| §2.5 | 核对与指令规则（I1–I4、R1–R5） | 结论须有行号背书；指令须有唯一锚点 |
| §2.6 | 命令行讲解规则（C1–C6） | 每条命令须讲清命令、选项、参数与危险后果 |
| §3 | 归档规则 | 触发时机与归档内容清单 |
| §3.5 | 生成物缓存规则（G1–G5） | 源码变更后须强制重建并核验缓存 |

该文件不是一次性制定的。**每一次事故都转化为一条编号规则**，这是本协作区别于常规用法的核心。

## 二、约束的演进：事故驱动

| 日期 | 触发事件 | 新增约束 | 若缺失会怎样 |
|---|---|---|---|
| 10-07 | 模型声称"已核对通过"，实际磁盘上并不存在该代码，静默失效的 bug 被带到综合阶段 | **§2.5 R1–R5**：每条结论须附行号；未出现者须写「未找到」；不得由"已下指令"推断"已存在" | 结论不可复核，错误被上游继承 |
| 10-07 | 修复源码后重新综合，综合仍使用缓存中的旧副本（时间戳落后源文件 18 分钟） | **§3.5 G1–G5**：两阶段重建 + 核验 `.gen` 缓存时间戳与内容 | 构建产物与源码不一致，且无任何报错 |
| 10-23 | 模型直接给出命令而未解释 | **§2.6 C1–C6**：命令、选项、参数、危险后果逐层讲解 | 无法在实操中积累对工具的理解 |
| 全周期 | 单个问题可能无限期消耗时间 | **§6 三十**分钟规则：一个问题纠结超过 30 分钟立即换路 | 项目节奏失控 |

《协作约定》§2.5 的一句话原则，可直接概括本协作的证据标准：

> **没有原文行号背书的"✅"，是假的 ✅。**
> **工具不会撒谎；人工核对会。**

## 三、五个方向性判断

以下五项贯穿项目全周期，各自对应一次**由本人提出、改变了技术路线或验收标准**的判断。

### 3.1 证据的最小单位是行号，而非陈述（2026-10-07）

**背景**：模型在一次代码核对中给出了完整的核对表并标注通过，但被核对的文件实际不存在。
该缺陷（`reg_wave_addr` 无驱动）未被发现，直到综合日志的 `Synth 8-3848` 警告将其暴露。

**判断**：问题不在"模型会犯错"，而在**验收标准允许了不可复核的结论**。
"我检查过"是一种陈述，不是证据；磁盘上的字节才是。

**对协作的改变**：将核对从"汇报"改为"举证"——每条结论必须附 `grep`/`read` 的原文行号；
要核对 N 项就须出示 N 条证据；证据不足时须明写"无法确认"而非标为通过。

**结果**：此后四周内未再出现假核对；所有源文件结论均可回溯到行号。

---

### 3.2 流程的可靠性必须制度化，不能依赖注意力（2026-10-07）

**背景**：修复 IP 源码后重新综合，`Synth 8-3848` 警告依旧存在。核查发现源文件时间戳为 22:28:55，
而综合使用的缓存副本为 22:10:41——**综合确实重跑了，但使用的是旧副本**。

**判断**：这不是偶发失误，而是工具机制决定的系统性风险。
IP 打包流程中，部分 HDL 在 `component.xml` 内无校验值，其变更不会触发缓存失效。
既然机制不可靠，就必须以流程强制替代。

**对协作的改变**：重建拆为两阶段——`rebuild_phase1.tcl` 删除 `.gen` 缓存，
`rebuild_phase2.tcl` 执行综合与实现；且 **phase1 之后必须核验缓存内容**（检查
`ipshared/*/hdl/` 是否包含本次修改的版本号或新增信号名），核验通过方可进入 phase2。

**结果**：本项目 6 次重建全部一次通过，未再发生"源码已改、综合未改"。

---

### 3.3 在具备复现手段之前，不做修改（2026-10-11）

**背景**：板级一次写操作导致整机冻结。模型连续提出六个假设并逐条修改，
每个假设都被排除，耗时接近一整个工作日。

**判断**：六个假设全部失败并非运气问题，而是**方法问题**——
在无法复现故障的条件下，任何修改都无法被验证，本质上都是赌博。

**对协作的改变**：要求先在 xsim 中复现板级现象（构造"写地址先于写数据到达"的时序），
确认复现后再修改 RTL。复现成功时，根因（写通道的时序竞争）随即明确。

**结果**：一次修复通过；该方法此后成为默认流程——**可复现性先于修复**。

---

### 3.4 结论的最小强度是"等价"，不是"接近"（2026-11-03）

**背景**：滤波链首次实现后 WNS 为 −6.363 ns，须拆分流水线。
拆分改变了时序结构，必须回答一个问题：**算法是否被改变。**

**判断**：模型最初以"误差仍在可接受范围"作为论证，该论证不可用——
若只要求"接近"，则无法区分"结构优化"与"算法退化"，两者在数值上表现相似。

**对协作的改变**：确立两条并列标准——

1. **等价性**：拆分流水线后，先重跑 `compare_rtl.py`，要求与 Python 定点模型
   **2000/2000 逐位相同、偏移 +0**，方可重建；
2. **多源交叉**：任何涉及时序或速率的结论，须由至少三个相互独立的量互证，
   单一寄存器读数不足以支撑。

**结果**：三次重建中功能零回归；板级时钟的确认（BD 配置 100 MHz，实际 62.5 MHz）
由 `Clocks` 读数、20 秒检测计数、每拍采样点数三个独立量共同锁定，
并一次性解释了此前三个看似无关的异常。

---

### 3.5 创新性是最大缺口，但不能以技术栈齐备来填补（2026-11-04）

**背景**：对照竞赛评分表，性能与正确性两项数据完整，而"创新性与应用价值"占 30 分，
是本项目的结构性短板——其技术内容为陷波、低通与 Pan-Tompkins 的组合，均属既有方法。

**判断**：两点同时成立——**必须补充实质创新，但不能以清单式技术栈充数**。
模型曾提议引入 AXI DMA 与 HLS 以"补齐技术栈"，该提议被否决：
原始波形数据率为 500 B/s，DMA 的固定开销高于其吞吐收益，
引入它满足的是清单而非问题，属于评分表明确警示的"以显著资源代价换取有限收益"。

**对协作的改变**：要求创新点必须同时满足三条——**有本项目自身证据支撑、有明确应用价值、
可在剩余工期内完成验证**。据此确定单导联三参数方向：

| 判据 | 该方向的对应证据 |
|---|---|
| 有自身证据 | 项目中已多次出现"数据不可信而无法判断"的情形，信号质量评估是真实需求 |
| 有应用价值 | 一条导联输出 HR、HRV 与呼吸率三个生理参数，可穿戴设备可省去独立呼吸传感器 |
| 可验证 | 以注入已知参数、检验能否还原的方式验证，判据可证伪 |

**结果**：三参数的验证结果为 HR 71.97 BPM（真值 72）、
呼吸率 12→11.8 / 15→15.0 / 18→18.2 次/分（判据误差 < 0.5，实测最大 0.2）。
该判据同时检出一处算法缺陷（高通拐点设置导致基频被滤除、仅余二次谐波），已修正。

## 四、对模型输出的验收标准

上述判断最终收敛为一组可执行的验收条件：

| 维度 | 标准 | 反例（已被拒绝的输出） |
|---|---|---|
| 证据 | 结论须附行号或实测数据 | 无行号的"已核对" |
| 等价性 | 结构变更须通过逐位比对 | "误差在可接受范围" |
| 复现性 | 故障须先复现再修复 | 连续假设与连续修改 |
| 必要性 | 新增功能须论证其解决的问题 | 为补齐技术栈而引入 DMA |
| 可证伪性 | 算法须有注入已知量的验证 | "波形看起来正确" |

## 五、协作的边界

以下事项不交由模型决定，且经实践证明不可让渡：

| 事项 | 原因 |
|---|---|
| 硬件操作的执行 | 模型的判断依据是本人提供的测量数据，其本身无法接触物理世界 |
| 方案的必要性判断 | 模型无工期压力，其倾向是"增加"而非"取舍" |
| 结论的采纳 | 模型会顺着提问者的假设生成自洽的解释；须由本人以数据否决 |
| 项目的方向与优先级 | 分值分布与工期的权衡属工程管理，非技术问题 |

本项目中被本人以数据否决的模型结论共七项，涵盖抑制比误判、伪周期、
比特流版本错误与判据本身失当，逐条记录于 `report/WORKLOG.md`。
这些否决构成了项目推进的主要方式。
